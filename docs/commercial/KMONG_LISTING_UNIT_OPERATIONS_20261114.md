## 실행 운영 규칙

1. **관리 키:** 각 작업은 `service_id`를 필수 식별자로 삼는다. 원천별 repo/branch/HEAD와 최종설계·보안/권리/테스트 증거는 하위 구성요소로 참조한다. 내부 제품별 개발은 계속할 수 있지만 크몽 상품화 판단은 단일 SKU 작업판에서 한다. 각 SKU는 중복 없는 고객 문제/산출물/판매 범위가 있어야 한다.
2. **BASE 단계:** 해당 서비스의 기본형 기능 범위, 고객 입력·납품 출력, Windows/브라우저/로그/안전, 라이선스·NOTICE·개인정보·유지보수, 매뉴얼·샘플·디자인·가격/환불·사용자 GO가 확인된 경우에만 `BASE_COMMERCIAL_READY`; 내부 기술 95%로 대체 불가. 출시 전까지 HOLD.
3. **선등록:** 기본형의 독립 사용과 실제 판매 가능성이 검증되면 상품명은 상위 확장을 허용하는 ‘고객 문제’ 중심으로 작성한다. 현재 제공하지 않는 고급 모듈은 상세설명에 **향후 개발 계획/미포함/일정 미확정**으로만 적는다. 미구현 기능을 구매 가능한 옵션·기본 제공 서비스로 게시하지 않는다.
4. **EXTENSION 단계:** 연결 원천 제품 완성→동일 SKU 기존 기능 회귀→통합 데이터/API/권한/파일 호환·가격/지원/매뉴얼/이미지 검수→사전 OWNER GO→기존 게시글 옵션/설명/대표 이미지/제목 수정. 실제 플랫폼 수정 승인·후속 검토/제한을 확인하며 ‘7영업일 내 반드시 승인’ 또는 ‘수정 즉시 무조건 승인’을 보증하지 않는다.
5. **게시 상태와 개발 상태 분리:** `BASE_READY / EXTENSION_READY / PRODUCT_NOT_VERIFIED`는 내부 작업 상태이고 `미등록 / 심사중 / 등록완료 / 판매중지 / 비공개 / 게시삭제`는 외부 게시 상태다. 등록완료는 실제 URL·날짜·증거 후에만, 기존 등록완료 이력은 어떤 후속 수정에서도 절대 삭제하지 않는다.
6. **소유자 개입 최소화:** 각 SKU마다 고객 대상 제목/범위/기능/가격/이미지/주의사항을 준비해 일괄 승인 요청한다. 개별 개발 담당자의 [작업중], [사용자 개입 필요], 공식 최종완성률, 실패 이력은 계속 독립 추적한다. 동일 기능을 SKU 여러 곳에서 재사용해도 해당 SKU의 전체 고객·권리·통합 검증 없이 진척률을 전파하지 않는다.
7. **기존 상품 보호:** 기능이 아예 다른 신규 제품으로 변하는 편집은 금지한다. 구매 목적과 납품 산출물이 달라지는 경우 새 고유 SKU를 사전 분류한 뒤 크몽 정책을 별도 확인한다. 이미 접수한 주문 조건도 소급 변경하지 않는다.
8. **고정 정본:** 원천 29종→19개 SKU, 19개 `service_id`, 원천 원래 repo/branch/기능·상태/점수, 현재 등록 이력, 기존 작업 표식 전부 불변. 권한·보안·원본 데이터·해커톤 브랜치·Vercel 프로젝트·유료 배포/검증 변경 없음.
