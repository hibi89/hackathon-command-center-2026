# 해커톤 공통 작업 순서 최적화 규약 — 선행 개발·일별 100%·차단 관리

> **사용자 승인 2026-10-24 KST.** 이 문서는 KIC·PayPal·UGREEN 및 향후 신규 해커톤에 적용되는 **상위 운영 원칙**이다. 각 대회 원본 일별 계획/작업 범위/기한/품질은 변경하지 않는다.

## 1. 결론: 순서는 유연, 완료 기준은 엄격
- 당일 계획 작업을 검증 기준까지 완료하면, **다음 날짜/다음 순번 중 바로 진행할 수 있는 작업을 선행 실행해도 된다**. 더 효율적이면 계획상 일자를 건너뛰어도 된다. 사용자 재승인을 매 순서 변경마다 받을 필요는 없다.
- 순서 최적화는 **의존성 충족 + 작업의 실효성 + 테스트 증거**를 바탕으로 한다. 달력 날짜가 빠르다는 이유만으로 BLOCKED/UNVERIFIED 업무를 실행 가능하다고 표시하지 않는다.
- **필수 선행 조건이 충족되지 않은 후속 기능을 '완료'로 간주하거나 실제 외부 기능 성공을 추정해서는 안 된다.** 분리 가능한 mock/offline 작업은 그것만 완료로 기록한다.
- 대회별 개발 총괄(각 1개 채팅)이 현재 `lead/*`에서 직접 구현·테스트·검수·커밋한다. 다른 작업자 채팅은 만들지 않는다.

## 2. 다음 실행 작업 선정 알고리즘 (`ㄱ` 포함)
1. 현재 승인된 범위의 대회별 원본 일정표·실적판·최신 HEAD/CI를 읽는다.
2. 대기 작업을 `VERIFIED_DONE`, `READY`, `IN_PROGRESS`, `BLOCKED_EXTERNAL`, `BLOCKED_DEPENDENCY`, `NOT_TESTED`로 나눠 중복 작업을 방지한다.
3. **실제 접근 권한/SDK/계정/실데이터가 없어 막힌 작업은 BLOCKED**로 유지한다. 사용자 조치·외부 답변이 필요하면 구체적으로 적고, 사용자 호출 때마다 무의미한 동일 방법 재시도 금지.
4. 준비된 작업 중 **(a) 다른 기능의 선행 기반, (b) 마감 리스크 감소, (c) 빠른 독립 검증, (d) 검증 가능한 품질 기여** 순으로 우선순위를 판단한다. 원본 일정과 달라진 이유를 1~2문장으로 기록한다.
5. 한 번에 **하나의 검증 가능한 작업 단위**를 수행한다. 코드→자동 테스트→원격 커밋/CI(가능한 경우)→결과 업데이트를 같은 작업에서 완료한다. 최소 기능을 새로 작성해도 전체 에이전트/실서비스 완료라고 주장하지 않는다.
6. 차단 원인이 해소되면 원본 일정상 누락된 필수 게이트를 복구하고 재검증한다. 이미 완료된 선행 코드를 재작성하지 않는다. 일별 원래 예산과 마감은 유지하되, 실제 잔여작업·이월을 별도 계산한다.

## 3. 퍼센트·시간의 분모 절대 혼용 금지
- **A. 달력일 계획 100%:** 해당 날짜 원래 확정된 업무별 검증 점수의 합계. 계획이 끝나면 그날 100%; 선행 작업으로 다른 날짜 작업이 끝나도 그날 완료율을 추가 가산해 100% 초과로 만들지 않는다.
- **B. 과제 단위 100%:** 개별 작업/마일스톤의 고유 완료 게이트. 미래 예정 과제도 오늘 실제 검증했다면 `VERIFIED_DONE (completed_early)`와 실제 완료일·원래 예정일을 기록한다.
- **C. 프로젝트 전체:** 전체 범위가 별도로 가중치/증거로 정의되지 않았으면 **전체 %를 추정하지 않는다**. 1일/일부 기능 100% ≠ 제출 준비 100%.
- **D. BLOCKED:** 선행 개발로 다른 부분이 완료되어도 해당 차단 과제의 완료율을 변경하거나 사후에 조용히 분모를 축소하지 않는다.
- **E. 잔여시간:** 남은 기준 개발 시간과 별도 오류/복구 예비를 보수적으로 분리하고, 외부 승인·접근 기다림은 `UNKNOWN/별도`. 실측하지 않은 시간을 실측이라고 쓰지 않는다.
- 선행 완료일을 오늘 작업과 미래 계획일 양쪽에 표시할 수는 있으나 **완료 건수·시간·가중치를 이중 계산하지 않는다**.

## 4. 변경 때 기록할 최소 9항목
- `execution_date_kst` 실제 실행일 / `planned_slot` 원래 계획일
- `task_id` 및 어떤 전후 관계를 바꾸었는지
- `dependency_gate`: 충족·부분 충족·차단 사항과 근거
- `status`: DONE/READY/BLOCKED 및 TESTED/NOT_TESTED 구분
- `evidence`: 커밋 SHA, CI URL, 테스트 통과/실패, 실 API/브라우저 검증 여부
- `daily_progress`: 그날의 원래 100점 기준 완료율
- `task_progress`: 선행 완료 과제의 별도 완료율(해당 시)
- `remaining_work`: 남은 순작업 시간 + 별도 예비 + 외부대기 미정
- `next_unblocked_task`: 가장 효율적인 실제 다음 일과 순서 변경 사유

대회별 정본 `LEAD_ACTIVE_WORK.md`, `DAILY_PROGRESS.md`/원장, `STATUS.md`, `HANDOFF.md`, `TO_HACKATHON_LEAD.md`에서 필요한 기록을 갱신한다. 문서가 없는 경우 현재 원장 구조를 존중하고 증거를 적절한 파일에 남긴다.

## 5. 경계
- **금지:** 실 SDK/API/기기/결제/권한 검증 없이 완료 주장, 테스트 실패 은폐, 기존 완료율 새 분모로 희석, 작업 중복, 사용자 승인 없는 유료 사용/실결제/범위축소/제출, 고객 데이터 공개, 강제 푸시.
- **유지:** 2026 KIC/PayPal/UGREEN 기존 공식·내부 마감, 원본 일별 계획, 0원 신규 지출 원칙, 사용자 명시 승인 게이트, 현행 4개 채팅 구조.
- 이 규약은 **GitHub 기록을 통한 비동기 인수인계**다. AI 채팅을 자동 실행하거나 백그라운드 감시하지 않는다.
