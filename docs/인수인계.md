# 해총 공통 개발 인수인계 — 새 채팅에서 실제 작업 이어가기

> **목적:** 새 채팅마다 긴 인수인계 메시지를 다시 쓰지 않고, "OO 작업자야. 해총 인수인계.md 읽고 작업 이어가라. ㄱ" 한 줄로 **해당 프로젝트의 실제 GitHub 상태를 재확인한 뒤** 안전하게 개발을 재개한다.
>
> **적용:** 해총이 관리하는 각 제품·개발 프로젝트. 이 파일은 공통 **실행 절차**이며, 제품별 확정 최종설계·AGENTS·REQ·권한·승인 규칙을 덮어쓰지 않는다.
>
> **중앙 위치:** `hibi89/hackathon-command-center-2026@kmong-productization:docs/인수인계.md`
>
> **중앙 정책 정본:** [OWNER DEV EXECUTION CANONICAL §0J](strategy/OWNER_DEV_EXECUTION_CANONICAL_20261116.md#0j-owner-current-model--swu-we--high-accountability--2026-11-18-kst-최신-사용자-지시), [GPT6 HIGH STANDARD WORK UNIT §0E](strategy/GPT6_HIGH_STANDARD_WORK_UNIT_20261117.md). 항상 원격 최신 내용 확인. 이 문서와 충돌하면 사용자의 더 최근 명시 지시, 프로젝트별 고유 안전·최종설계, 중앙 최신 정책을 우선 적용한다.

## 1. 새 채팅의 프로젝트·임무를 먼저 고정한다

1. 사용자가 지정한 **프로젝트/제품명·담당 역할**을 현재 채팅의 임무로 고정한다. `ㄱ`·`ㄱㄱ`을 받더라도 다른 프로젝트나 해총 관리 업무로 임의 전환하지 않는다.
2. 저장소/브랜치가 메시지에 없더라도 먼저 해총 중앙 프로젝트 원장·프로젝트 문서·GitHub의 실재하는 저장소를 확인해 해당 프로젝트의 **원본 repo, 개발 branch, 최종설계 branch(별도인 경우)**를 찾는다. **추측으로 repo·branch를 선택하지 않는다.** 후보가 여러 개로 구분 불가하면 한 가지 필수 확인만 요청한다.
3. **해총 채팅 자체**에 별도 임무를 지정하지 않고 `ㄱ`이라고 하면 중앙 GitHub App → 서명 HMAC Webhook → 기존 Vercel → GitHub Actions → 원장 자동화 임무만 재개한다. 다른 제품 작업은 그 제품 채팅에서 실행한다.
4. 새 채팅의 첫 작업은 인계글을 그대로 믿는 것이 아니라 **현재 원격 GitHub HEAD와 실제 소스**를 확인해 이전 작업의 완료·미완료를 재구성하는 것이다.

## 2. 해당 프로젝트 GitHub의 확정 최종설계도와 실제 상태를 확인한다

다음은 **조회 순서**다. 지시의 권한 우선순위와 혼동하지 않는다.

1. 대상 `repo / branch / 원격 HEAD 전체 SHA` 확인; 필요 시 중앙 `kmong-productization` 최신 HEAD도 확인.
2. `AGENTS.md` 및 프로젝트 고유 안전·개발 지침 확인.
3. `HANDOFF`, `STATUS`, 작업 큐, 차단/격리 이력 확인.
4. `REQUIREMENTS`, **승인된 FINAL BLUEPRINT/최종설계**, 계약·REQ↔SWU·의존성 DAG·allowed_paths·수용조건 확인. 최종설계가 별도 브랜치에 있다면 그 브랜치와 정확 SHA도 확인.
5. 현재 실제 BE/FE/API/DB/CLI/Controller 코드와 기존 커밋을 읽고 문서의 완료 주장과 대조. 누락·모순은 `미확인` 또는 코드 근거에 따라 정정.
6. 중앙 해총 최신 공통 정책의 적용 부분을 확인하고, **제품의 확정 기능 범위/권리/안전 게이트를 임의 축소·변경하지 않는다.**

**판단 권한:** 사용자 현재 지시·사전 승인 > 제품 최종설계 및 고유 안전/대회 규칙 > 해총 최신 공통 정책·프로젝트 AGENTS > 실제 코드/HEAD/실행 증거 > HANDOFF/STATUS/큐 > 과거 대화·문서. 실제 완료 여부는 코드와 실행 증거로 판단한다.

## 3. P1 구현을 먼저 완수하고, P2 검증은 뒤로 모은다

### P1 — 최종설계의 실제 기능 구현 100% 후보가 우선

- 실제 **백엔드 핵심 로직 → 저장/DB → API·CLI·Controller·실행 경로 → 핵심 오류·복구 분기 → 설계에 필요한 프론트엔드 및 BE 연결**을 구현한다. 의존성이 있다면 호출자→피호출자까지 연결된 수직 기능을 우선한다.
- `TODO`, 목업만, 화면 캡처, 테스트/문서 추가, 상태표 업데이트만으로 기능 완료를 인정하지 않는다.
- **전체 CI 반복 실행/결과 폴링, 대규모 테스트 하네스 작성, 종합 통합·회귀·E2E, 브라우저/시각·반응형, 전수 보안감사, 실기기/실모델 검증은 P2 큐에 기록하고 뒤로 미룬다.** P1을 불필요한 검증 반복으로 지연시키지 않는다.
- **단,** 해당 수정에 필수인 국소 syntax/type/smoke와 인증·인가/비밀·원본·DB 손실/복구·F18 등 **즉시 안전검사**, 이미 강제된 자동 CI·브랜치 보호는 유지한다. 필수 CI를 끄거나 보호를 우회하지 않는다.
- 각 기능의 코드 경로가 완성됐지만 전체 검증 전이면 `IMPLEMENTED_UNVERIFIED` / `SOURCE_COMPLETE_P2_PENDING`으로 구분한다. P1 100% 후보 ≠ 기능·보안 검증 100%, 출시 GO, 크몽 등록 완료.

### P2 — 구현 100% 후보와 프로젝트 고유 게이트 통과 이후

- 전체 CI/빌드·기능·보안·통합·회귀·복구·브라우저/실기기/실모델 검증을 일괄 수행한다. 발견한 결함을 수정하고 재검증한다.
- 승인된 독립 기술·보안 검수, Astra UI/UX 검수, High 최종 인수는 **실제로 수행된 결과**만 인정한다. 본인이 작성한 코드의 자체 점검을 독립 감사라 하지 않는다.
- 검증 완료·제품 실사용·Production·상용 출시·상품 등록은 각기 별도 승인/증거가 필요하다.

## 4. `ㄱ` 또는 `ㄱㄱ` = 현재 고정된 임무의 다음 **실제 작업 실행**

- `ㄱ`과 `ㄱㄱ`은 동일한 재개 명령이다. 장문 설명이나 반복 상태보고를 요청하는 명령이 아니다.
- 매회 **최신 HEAD → 코드/큐 기준 READY 재평가(CPAA) → 실제 기능 코딩(WE) → 필수 국소 검사 → 안전한 GitHub 반영 → 커밋 전체 SHA 대조** 순서로 실행한다.
- **1 SWU**는 의미 있는 실제 소스 기능을 한 번의 웹 Sol High 코딩으로 완료 후보까지 만들 수 있는 독립 수직 단위다. 기존 REQ·SWU ID, 의존성, S/C/I/D/U, allowed_paths, 수용조건, 실패 이력은 보존한다.
- 한 회차에 독립·위상정렬된 실제 READY **1~6 SWU**를 안전하게 진행한다(일반 3~6 목표, 난제 1~2 가능). 임계경로·후속 차단·위험·충돌·총완료시간을 고려하며 숫자를 채우려고 가짜 작업을 만들지 않는다.
- 실제 코드와 SHA가 진전되면 최신 HEAD/READY를 재확인하고 같은 회차에 가능하면 다음 웨이브도 진행한다. 동일 ref 동시 쓰기는 금지하고, 멀티 작업자 병렬은 별도 브랜치·소유권·통합 조건이 확인된 경우에 한한다.
- 웹 GPT의 조회/도구 호출만 일부 병렬 가능하다. 독립 모델 여러 명이 동시에 구현했다고 주장하지 않는다.
- 접근 도구/쓰기 권한이 없으면 작업하지 않은 구현·커밋을 완료로 표시하지 말고 무엇이 막혔는지 정확히 알린다. 백그라운드 완료를 약속하지 않는다.

## 5. 장애 처리: 2+2 격리와 독립 READY 지속

- 일반 코드·설계 오류는 현재 P1 작업자인 웹 GPT-6 High가 먼저 원인 분석·수정한다. **실제로 코드를 시도했지만 무진전인 초기 2회**에만 해당 SWU를 `ISOLATED_REDESIGN_PENDING`으로 격리한다.
- 방법을 바꿔 설계·구현을 다시 시도하고 **추가 2회 실패(누적 4회)**라면 `SOLMAX_BATCH_PENDING`으로 증거·SHA·실패 원인·대안을 모아 지원을 요청한다. 단순 `ㄱ`, 조회, CI 폴링, 같은 방법 재실행, 문서 변경은 실패 횟수로 세지 않는다.
- 임계경로의 고위험 신뢰·암호·DB/권한 문제는 High의 원인·대안 분석 후 실패 0회에도 전문 지원을 요청할 수 있다. **Codex=코드/보안/DB/CI**, **Work=실브라우저·로그인·관리화면/현장 E2E**를 필요에 따라 구분하되 모델 가용성 미확인이면 `MODEL_UNVERIFIED`다.
- 차단 과제만 HOLD하고 안전한 독립 READY의 실제 구현은 계속한다. 전문 지원 요청이 사용자 GO·원본 접근·유료 사용 승인으로 바뀌지 않는다.

## 6. 구현완성률·검증완료율을 분리 보고한다

- **구현완성률:** 확정 최종설계의 실제 기능 코드 구현 후보 진행.
- **검증완료율:** 승인 수용조건 중 실제 PASS 완료 진행.
- 정당한 분모·가중치가 있으면 근거대로 계산. 없으면 `완료 SWU / 전체 SWU`, `완료 REQ / 전체 REQ`, `UNASSESSED`를 명시하며 임의 %·+1%p·100%를 만들지 않는다.
- 매 회차 결과는 짧게: `repo@branch@전체 HEAD SHA / 완료 SWU·REQ / 실제 구현 기능·경로 / 국소 PASS·FAIL·SKIP·NOT_RUN / P2 DEFERRED / 공식 진행률 또는 UNASSESSED / HOLD·격리·다음 READY`.
- 정책 문서만 수정했다면 기능 진척은 **0**이다. 정확한 실행 증거가 없는 테스트·모델 검수·배포는 `NOT_RUN`/미검증·미적용으로 표시한다.

## 7. 안전 및 GitHub 반영 원칙

- **별도 사용자 승인 필요:** 유료 결제, 고객·민감 원본 외부 전송/변조, 위험 DB·권한·보안 변경, 기존 기능/범위 축소, main 병합, Production/도메인/환경변수/연동 변경, 상용 출시.
- 무료·로컬 우선. 토큰·비밀키·`.env`·고객 원본을 공개 GitHub에 커밋하지 않는다. 원본/백업/Git 이력 보존, force push·임의 커밋 이메일 변경 금지.
- 코드 반영은 목표 **제품 원본 저장소/승인된 작업 브랜치**에만 수행한다. 해총 공통 문서를 읽었다고 각 제품의 브랜치에 이미 반영된 것으로 간주하지 않는다.

## 8. 새 채팅 인계 시 최신 상태를 GitHub에 남긴다

중요한 채팅 전환/마일스톤 시 해당 프로젝트의 STATUS·HANDOFF를 실제 상태에 맞춰 최소 수정한다. 최소 인계 필드는 다음과 같다.

```text
프로젝트 / 역할 / 원본 repo / 작업 branch / 정확 원격 HEAD SHA
확정 최종설계 문서 경로·설계 branch·기준 SHA / REQ·SWU 큐
P1 또는 P2 단계 / 구현 완료 후보 / 남은 READY / 차단·격리와 실패 근거
구현완성률·검증완료율(근거 없으면 UNASSESSED)
실제 검사 PASS/FAIL/SKIP/NOT_RUN 및 P2 이관 목록
Production / 고객 원본·백업·권한 / 별도 승인 필요 항목
다음 ㄱ에서 진행할 실제 소스 작업 / KST 기록 시각
```

GitHub 쓰기가 안 되면 **미반영**임을 밝히고 짧은 인계 텍스트를 제공한다. 상태 불변이면 빈 문서 커밋을 만들지 않는다.
