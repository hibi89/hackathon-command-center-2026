## 2. 개발 가속 규칙 — CI를 마지막으로 모으되 위험 검증은 유지
1. P1에서는 **전체 CI를 매 작업마다 기다리지 않는다.** 단, 구현자가 도구로 수행 가능한 최소 문법·타입·컴파일·변경 범위 스모크/계약 검증은 선택적으로 즉시 시행할 수 있다. DB 마이그레이션, 데이터 삭제, 인증·권한·결제, 외부 통신, 경로/파일 안전, 고객 원본, 비밀 노출에 영향을 주는 변경에는 관련 안전 검증을 미루지 않는다.
2. 이미 자동으로 발동하는 GitHub Actions와 브랜치 보호/필수 검사·보안 게이트는 **무단 비활성화하지 않는다**. 비용이나 실행량을 줄여야 하면 코드/문서 경로 필터, 기능 브랜치와 승인된 워크플로 설정 등 안전한 대안을 별도로 비교하고 사용자 승인을 구한다.
3. P1 단계의 미실행 테스트를 PASS로 표시하지 않는다. 후단 CI에서 발견한 버그가 커질 수 있음을 인정하고 원인을 분류하여 최소 수정한다. 무의미한 CI 재실행·빈 커밋·무한 재시도 금지.
4. 한번의 `ㄱ`마다 P0 반복 조사/설명보다 실제 코딩·정확 SHA·검증 가능 진전에 우선순위를 둔다. 가능한 여러 기능을 묶고 CI/도구 대기 중 독립 작업을 병렬화하되 동일 파일 충돌·승인 없는 외부 호출·무단 상품 전환은 금지한다.
5. 실물 검증이 불가능하면 `NOT_VERIFIED`/HOLD로 남기고 증거 없는 100점 최종 판정은 하지 않는다. 실행 안 되는 코드를 완성품이라 부르지 않는다.

## 3. 진척률 이중 기록(기존 공식률 무변경)
- `IMPLEMENTATION_SCOPE_PROGRESS`: 최종설계 BE/FE REQ-ID 중 코드 구현 확인 상태(IMPLEMENTED / PARTIAL / NOT_IMPLEMENTED)를 별도로 기록. 추적표 범위 미확정이나 가중치 미승인 시 숫자 임의 생성 금지. `IMPLEMENTATION_100_CANDIDATE`는 코드 위치만 있다는 뜻이지 작동 검증 PASS가 아니다.
- `OFFICIAL_FINAL_BLUEPRINT_COMPLETION`: 사용자 승인 100점 전체 최종설계 기준 **검증된** 수용항목 가중치 합만 계산. 승인 가중치/증거 부족이면 `UNASSESSED` 유지. 기존 85·95 등 과거 엔지니어링 추정치 덮어쓰지 않는다.
- 매 회차 보고: `원천 repo/branch/SHA | 구현 전→후 (근거) | 공식 검증 전→후 또는 UNASSESSED | 완료 REQ | PASS/FAIL/SKIP/NOT_RUN | 차단·다음 실행`. 공식 수치 정체라도 구현 항목 및 실제 코드 변경 증거를 보여준다. 숫자 채우기용 가짜 +1%p 금지.
- `BASE` 상품과 전체 `EXTENSION`은 등록 정책에 따라 별도 판매 준비 트랙으로 구분 가능하지만 **사용자가 전체 최종설계 100% 구현을 지시한 제품의 범위를 몰래 축소/삭제하면 안 된다**. 전체 P1 구현 우선, BASE 조기 판매는 별도 사용자 GO 필요.
