# 사용자 최상위 지시 — 전 레포지토리 개발 표준: 설계 → 1~2일 MVP → 기능·품질 → 프론트·완성

- 확정일: **2026-10-28 KST**
- 발령: 사용자(최종 승인권자)
- 적용: **앞으로 생성하는 모든 GitHub 저장소·제품**, 그리고 이미 개발 중인 프로젝트의 **다음 실개발 단계**. 전담자가 누구든 동일하게 준수한다.
- 본 문서는 **개발 순서·속도·검수의 상위 지시**다. 해커톤 공식 규정·제출시각, 개인정보·권리·자금·외부 계정 승인, 원본 데이터 보호 등 필수 제한은 그대로 유지한다.
- 원본 기능 범위를 축소하는 판단과 일정 지시 변경은 사용자만 승인한다. 중앙 해총이 다른 레포를 임의 수정하거나 대화방을 자동 지휘하지 않는다.

## 1. 최종 목적물부터 설계 — DAY 0
1. 사용자가 달성하려는 **최종 제품**을 먼저 한 장 수준의 실행 가능한 설계로 정의한다. 핵심 사용 시나리오, 입력→처리→출력, 구현 모듈·주요 연계, 실제 완료 판정, 범위·외부 의존성을 적는다.
2. 1~2일 MVP에서 만들 **최소한의 진짜 작동 수직 슬라이스**를 골라 최종 목표와의 연결 관계를 명시한다. 설계 문서 반복·불필요한 다이어그램에 개발 시간을 쓰지 않는다.
3. 전체 범위와 MVP를 혼동하지 않는다. MVP는 진행 방식이지 원래 최종 목적물의 자동 폐기·축소 승인이 아니다.

## 2. MVP는 하루, 늦어도 이틀 — DAY 1~2
- **DAY 1 우선, DAY 2 이내** 실제 입력→핵심 처리→출력까지 돌아가는 최소작동단위를 코드로 구현한다.
- 예쁘지 않은 CLI·간단한 화면·최소 브라우저 UI라도 실제 핵심 동작을 증명할 수 있으면 된다. **작동에 필수인 최소 UI만** 만들며 디자인·애니메이션·꾸미기는 마지막으로 미룬다.
- 합성 테스트만 아니라 가능한 환경에서 실제 프로세스·HTTP·브라우저·파일의 **핵심 E2E 근거**를 남긴다. 불가능한 외부 연동은 `NOT_RUN/BLOCKED`로 표시하고 가짜 성공 처리하지 않는다.
- 사용자 승인 없는 외부 결제, 민감정보 업로드, 라이브 서비스 조작, 비밀키 커밋, 출처·권한 위반은 금지. **되돌릴 수 없는 손상 방지 등 최저 안전선은 MVP 때부터 필수**다.

## 3. 최종 설계도 대비 누락 기능 채우기 → 정확성·안정성·보안·오류 검증 — DAY 2~5
1. **원래 최종 설계와 현재 실행되는 MVP를 대조**하여 누락 기능을 작은 단위로 목록화한다. 문서 작업이 아니라 실제 코드 구현을 우선한다.
2. 작업 순위: **핵심 기능 미구현·실제 연결 실패 → 기능 정확성·오류 처리·상태 보존 → 보안·안정성·호환성 및 회귀검증 → 부가기능/미관**.
3. 변경할 때마다 필요한 최소 회귀테스트를 수행한다. 단위테스트 개수만 늘리지 말고 **사용자 흐름이 끝까지 작동하는지** 확인한다.
4. 이미 통과한 실험을 근거 없이 계속 반복하거나, 첫 MVP보다 문서·가짜 UI·장식에 시간을 먼저 쓰지 않는다.
5. 데이터·인증·라이선스·외부 API 등 **치명적인 위험**은 검증 후반까지 숨기지 말고 발견 즉시 차단/해결한다. 최종 검증에서는 보안, 정확성, 안정성, 오류 복구, 성능, 주요 환경 호환성을 제품의 실제 범위에 맞게 증명한다.

## 4. 프론트엔드 최종 정리 및 완성 — 원칙적으로 마지막
- 앞의 **핵심 기능과 주요 검증이 성립한 뒤** 최종 UI/UX·디자인·반응형·배포/패키징·매뉴얼 등 출고 품질을 완성한다.
- 앞 단계에서 필요한 최소 조작 화면은 허용하지만, **프론트엔드 완성도를 이유로 실제 기능 구현을 뒤로 미루지 않는다**.
- 최종 완료는 **실제 작동하는 최종 기능, 보안·안정성 검증, 실행·설치·제출 또는 납품 가능 증거**로 판단한다. 문서상 100%, 녹색 CI만으로 출시 성공을 선언하지 않는다.

## 시간표 — 3일 BEST / 4~5일 STANDARD / 7일 HARD LIMIT

| 경과 | 목표 | 감독 기준 |
| --- | --- | --- |
| DAY 0 | 최종 설계 및 MVP 핵심 경로 확정 | 원래 목표·완료조건 고정 |
| DAY 1 | 실제 동작 MVP 우선 완성 | 실행 코드와 증거 확인 |
| DAY 2 | MVP 최종 허용선 | **이 시점까지 불가하면 즉시 원인·차단·복구안 보고** |
| DAY 3 | **BEST: 최종 완성** | 원 설계 대비 미구현·검증 잔여 0 또는 명시적 예외 |
| DAY 4~5 | **STANDARD: 최종 완성** | 핵심 기능·검증·최종 UI·출고 준비 |
| DAY 6~7 | 최후 보완·최종 판정 | **7일 초과 전에 사용자에게 지시/범위 재검토 상신** |
| DAY 8+ | **정상 일정 아님** | 자동 연장·완성 주장 금지; 사용자 지시가 잘못 설정됐는지 포함하여 재평가 |

- 개발 일정은 **착수일(KST)부터 지난 날짜**로 관리한다. 별도 합의 없는 한 사람별 임의의 '집중일' 단위로 숨겨 연장하지 않는다. 실투입 시간은 알 수 없으면 별도로 `NOT_MEASURED`.
- **일주일은 사용자 지정 마지노선**이다. 초과 시 단순히 작업자를 탓하기보다 사용자의 지시/제품 범위/의존성/자원 가정부터 재평가한다. 미승인 임의 축소 또는 조용한 연장 금지.
- 이미 진행 중인 오래된 레포에 본 규칙을 과거 날짜부터 소급하여 '기한 초과 확정'으로 적용하지 않는다. **다음 작업의 재계획·우선순위**부터 적용하고 기존 공식 마감은 지킨다.
- 외부 계정·공식 실물 NAS·법적 권리·고객 승인 등 사용자 통제 밖의 블로커는 사실대로 보고한다. 7일 안에 해결될 것이라고 거짓 보장하지 않는다.

## 매 프로젝트 최소 증거 / 해총 감독
- `FULL_DESIGN`: 원래 최종 설계의 기능/수용조건 및 범위 변경 승인 상태
- `MVP_E2E`: 구동 명령, 입력→출력 증거, 테스트 날짜, Git SHA, PASS/FAIL/NOT_RUN
- `GAP_MATRIX`: 최초 설계와 MVP의 **실제 미구현 기능**만 추적
- `HARDENING`: 보안·정확성·안정성·오류 복구·호환성의 주요 시험 결과
- `FINAL_RELEASE`: 제품 실제 실행·사용자 승인·납품/공식 제출 영수증 여부
- `CLOCK`: 착수 KST, DAY 1/2 MVP, DAY 3/5 완료 목표, DAY 7 중단·재지시 판단 시점
- 해총은 감독 호출 시 **기능보다 문서만 증가하는지, MVP 실행 증거가 있는지, 일정이 3/5/7 기준을 이탈했는지**를 검토한다. 시정은 중앙에 기록하고 담당 레포 실제 반영은 별도로 확인한다.

**중요:** 이 지시는 7일 내 구현을 증명하거나 실제로 시간을 경과시킨 사실이 아니다. 본 공시는 **정책 문서 갱신**이며, 각 레포의 개발 코드·CI·공식 제출·기존 승인 상태는 변경하지 않는다.
