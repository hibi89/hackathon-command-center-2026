## 1. 개발 시작 전 반드시 고정할 것 — `PRODUCT_AND_INTEGRATION_BASELINE`

사용자가 말한 '프로그램들'의 표준 명칭은 **구성 요소/재사용 소프트웨어 모듈(Component & Dependency Inventory)**, 함께 묶는 전체 명세는 **제품·통합 아키텍처 기준선(Product & Integration Baseline)** 이다. 설계도를 수십 페이지 쓰라는 뜻이 아니라 **최대 1장 기본표 + 필요 계약**으로 확정한다.

**착수 기준선 8개 항목:**
1. **최종 만들 제품/고객가치:** 대회 출품용 제품명, 누구의 어떤 문제를 해결하는지, 입력/판단/출력, 실제 시연될 사용자 시나리오, 최종 기능 수용 조건. 제품 전체 목표와 초기 E2E MVP 범위를 **별개**로 기록한다.
2. **기술 스택 명세:** 언어/버전, 런타임, 주요 라이브러리·모델, 외부 API, DB/파일 저장, 인증, 테스트/CI, 프론트의 최소 조작수단, 배포/실행 환경을 **구체적 이름**으로 기록한다. 근거 없는 신규 프레임워크/서버 도입 금지.
3. **프로그램(구성 모듈) 인벤토리:** 필요한 기존 GitHub 레포·정확한 브랜치/SHA·모듈·소유자·재사용 기능·현재 작동/미검증·인터페이스·사용 라이선스/공개 권한. **신규로 개발할 것 vs 이미 있는 것**을 구분. 기능 요구만으로 코드가 존재한다고 가정하지 않는다.
4. **단일 메인 레포와 연동 방식:** 대회별 메인 저장소와 통합 브랜치가 백엔드의 단일 진입점/오케스트레이션·상태 관리 주체다. 다른 레포는 검증된 라이브러리/CLI/로컬 HTTP/파일 JSON 계약으로 연결. 비공개 코드를 공개 레포로 무단 복제하지 않는다. 새 레포/브랜치/앱 생성은 필요성과 사용자 승인 먼저 확인한다.
5. **작동 경로 계약:** 트리거 → 입력/권한 확인 → 전처리 → 핵심 판단(모델/규칙) → 명시적 승인(필요 시) → 외부 연동/DB 실행 → 결과 조회 → 감사/오류 복구를 한 줄로 연결한다. 각 경계의 입력·출력 JSON/스키마, 읽기/쓰기 구분, ID·중복 방지, 실패 시 재개 방법을 명시한다.
6. **비용·성능·안전:** 무료 한도·호출 횟수·토큰/스토리지·레이트리밋·로컬 자원/환경·timeout·retry/idempotency·비밀 관리·개인정보·데이터 원본 보호를 검토. 불확실 요소는 `BLOCKED/UNVERIFIED`.
7. **2개 이상 설계안 경량 비교:** (A) 기존 모듈 최소 연동 (B) 신규 통합 구현/교체를 **속도·비용·실증 가능성·유지보수·권리/보안** 기준으로 비교해 제안. 사용자 승인된 최적안으로 착수하며, 코드 진행 중 소소한 스택 변경은 계약/테스트에 영향이 없으면 담당 총괄이 기록 후 처리할 수 있지만 **기능·비용·데이터·권한·구조를 바꾸는 변경은 재승인**.
8. **완료 기준과 금지 범위:** 필수 E2E 시나리오별 `PASS/FAIL/BLOCKED/NOT_RUN`, 실제 외부 시스템 vs mock 구분, 제출물·공식 마감, 제외 또는 후순위 기능 명시. 별도 승인 없는 기능 축소 금지.

**착수 전 조건:** 최신 `HANDOFF→STATUS→AGENTS→REQUIREMENTS→소스`와 대회 규정을 확인하고 해당 기준선을 제품 메인 저장소의 단일 정본에 유지. 과거 기준선이 있다면 **최신 승인 변경점만 추가**하며 전량 재설계하지 않는다. 원본/실데이터 수정 전 백업·복원/현재 SHA 확인.

## 2. 구현 알고리즘 — 백엔드를 먼저 끝내는 48시간 집중 루프

**PHASE 0 / 착수 직전:**
- 메인 레포 HEAD와 구성 모듈 실제 소스·실행 가능성·권리 확인. 필수 모듈이 실재하지 않으면 대체 방법을 결정하여 **초기에 병목 제거**.
- 최종 제품을 기능별 작업 묶음으로 쪼개고, 의존성 그래프에서 **E2E 핵심 경로(critical path)**를 맨 앞으로 이동. UI 꾸미기·PDF/영상·소개글·반복 설계 회의는 후순위. 대회 공식 제출 리스크와 마감은 별도 추적.
- 단계별 최소 백엔드 수용 테스트 작성(정상/실패/권한/중복·데이터 무결성). 작은 설계 요약 후 **실제 코드 착수**.

**PHASE 1 / DAY 1: BACKEND SKELETON → FULL VERTICAL SLICE**
- 메인 레포에 실제 엔트리포인트와 통합 API/CLI, 최소 DB, 에러 모델, 필수 연결 어댑터를 연결한다.
- 기능 하나씩 문서·커밋하고 멈추지 말고 **연관 핵심 기능 여러 개를 연속 구현**한다. 최소 화면 또는 CLI만으로 실제 입력→처리→상태 저장→결과/감사 조회가 되어야 한다.
- 외부 실연동에 승인/장비가 필요하면 안전한 mock 및 보존된 실제 증빙으로 내부 경로를 검증하고, **실 API/NAS 미실행을 명시**한다. 모킹을 실증으로 둔갑시키지 않는다.
- 중간 보고는 작업 개수/코드 줄 수/CI 테스트 개수보다 **실제로 연결된 E2E 기능** 위주.

**PHASE 2 / DAY 2: 백엔드 기능 누락 제거와 진짜 통합**
- 최초 `PRODUCT_AND_INTEGRATION_BASELINE` 대비 백엔드 누락을 메우고, 입력/조회/처리/쓰기/감사/복구를 실제 실행한다.
- 각 단계가 별도 성공했다고 전체 통합 성공이라고 하지 않는다. **메인 레포에서 재현 가능한 단일 E2E 명령**과 각 결과가 필요하다.
- 실환경 차단이 있으면 승인 없이 우회하거나 POST·결제·쓰기 재시도하지 않는다. 독립 백엔드 기능은 계속 개발하면서 차단 항목을 `BLOCKED`로 분리한다.
- DAY 2 종료 판정은 `BACKEND_E2E_PASS` 또는 명시적인 실패/장애 보고다. **48시간 완성 보장 금지**, 미완료 시 즉시 Critical Path/Pivot 재평가.

**PHASE 3 / DAY 3~5: 품질과 외부 최종 게이트 → 프론트·제출**
- **실행 가능 백엔드 이후** 보안·정확성·오류·상태 보존·권한·실제 브라우저/API/실행기 회귀를 완료하고 UI/UX·디자인·영상·제출 패키지 품질을 마무리한다. 마감 위험이 임박하면 필수 제출 준비는 병렬 진행할 수 있으나 코어 개발을 밀어내지 않는다.
- 테스트/배포/제출/발표는 서로 다른 게이트. CI 녹색이나 문서 완성만으로 실작동/출고/공식 제출 완료로 판정하지 않는다. 현행 3/5/7 제품 출고 표준에 따라 지연은 숨기지 않고 재계획·재지시한다.

## 3. CI·테스트 처리 규칙 — '확인하고 넘어간다'의 정확한 뜻

1. **CI는 개발 중 비차단 병렬 검증:** 핵심 코드 묶음을 커밋/푸시 → CI run ID·SHA·상태 기록 → 다음 **독립적이고 안전한 작업** 즉시 진행. 긴 CI 완료를 기다리며 같은 화면을 반복 조회하지 않는다. 하루 종일 CI만 돌리고 기능이 늘지 않는 행동 금지.
2. **로컬 필수 스모크는 건너뛰지 않는다:** 수정한 기능의 빠른 스모크·정적 오류·데이터 손상/보안 가드는 해당 변경 전에/후에 실행. CI 결과가 필요한 의존 작업, 불안정한 인터페이스 위에서 진행하는 작업은 별도 게이트.
3. **실패/대기는 작업 추적:** `SHA | 테스트명 | 실행시각 | CI URL | PASS/FAIL/SKIP/RUNNING | 실패원인 | 다음조치` 한 줄 기록. CI 실패 시 원인을 코딩/테스트/의존성/환경으로 분류한다. 안전한 독립 작업은 계속하지만 같은 실패를 무시하고 릴리스하지 않는다.
4. **통합/릴리스 전 회수:** 마지막으로 변경한 SHA에서 필요한 전체 회귀·CI·실제 E2E와 보안 게이트가 통과해야 한다. 아직 RUNNING/FAIL/SKIP이면 `검증 대기/부분 완료`이며 제출·배포 성공 주장은 금지. 필수 checks 우회, 실패 테스트 삭제, 보안 게이트 무단 해제 금지.
5. **Stop & Pivot:** 같은 접근으로 근거 없는 실패 2회면 원인과 로그부터 분리하고 대안 비교 후 전환. 유료 CI/외부 API/결제/권한/데이터 전송은 사전 승인. API 한도 소모를 '속도'라고 오인하지 않는다.

## 5. `ㄱ` 실행 계약 / 보고 / 해총 감독

- 사용자가 `ㄱ`을 누르면 **계획 설명만 재작성하지 않는다**. 현재 승인된 작업 묶음의 **소스 수정 → 빠른 로컬 검증 → 다음 안전 작업 병행 → 기능 단위 커밋/푸시 → 통합 증거**를 도구·권한이 허용하는 범위에서 연속 수행한다. 독립된 작업들은 CI 대기 중 처리한다. API 호출이 불가능한 경우 허위 실행 결과를 만들지 않는다.
- 보고는 `실제 신규 연결 기능 / 본체 SHA / E2E PASS·FAIL·NOT_RUN / CI 상태·URL / 차단 / 다음 우선순위` 정도로 간소화. **확률·진척률·시간 절감률은 실측 근거 없으면 만들지 않는다.**
- 문서 갱신은 실제 완료된 주요 기능 묶음·설계 변경·채팅 인수인계 시 `STATUS/HANDOFF`를 현재 상태와 일치시키는 수준으로 실시한다. 매 단위 테스트마다 중복 문서 네댓 개를 갱신하지 않는다. `README`는 실행법이 바뀔 때 수정.
- 해총의 감독 질문 5개: (1) 제품/스택/재사용 레포가 **착수 전 확정**되었나? (2) 메인 저장소 백엔드 E2E가 오늘 실제로 증가했나? (3) CI 대기/문서/영상이 핵심 개발을 막고 있나? (4) 필수 보안/권리/외부 승인 차단이 있는가? (5) 마지막 검증 SHA가 실제 메인 브랜치 SHA와 일치하는가?
- **현 단계 이 문서는 중앙 상황실의 운영 정책 기록만 완료**. 각 해커톤 담당 리드 저장소 자동 반영·백엔드 코드 변경·실제 CI 실행·실제 외부 연동/배포·공식 제출을 뜻하지 않는다.

## 우선순위 및 충돌 규칙

**최신 사용자 제품·작업 우선순위 + 대회 공식/법률/권리/안전 제약 > 개별 제품 최신 확정 설계와 실제 실행 증거 > 본 문서의 일반 실행 방법 > 과거 설계·구형 프로세스.**

특히 `20261028_OWNER_UNIVERSAL_REPO_DELIVERY_STANDARD_3_5_7.md` 및 `DEV_ACCELERATION_AND_VERIFICATION_20261028.md`의 **MVP→품질→프론트, 비용 제로, 검증 정확성**을 보존하면서, 이번 정책은 그보다 **명시적인 사전 구성 확정·메인 레포 백엔드 집중·CI 병렬화**를 추가한다.
