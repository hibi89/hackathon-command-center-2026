4. **검증 이관 방식:** P2 검증 큐에는 `req_ids / test_scope / source_sha / risk / stage=P2 / status=DEFERRED`로 이관. Codex GPT-6.1 Sol Max가 P1 구현 100% 후보·고유 게이트 이후 **전수 syntax/type/CI, 보안·인증/인가/DB 무결성/복구, 통합·회귀·브라우저·실기기/실모델, 결함 수정·재검증** 일괄 수행. P2 작업은 P1 SWU 수·시도 예산에 미포함.
5. **P1 최소 안전선:** 기존 필수 자동 CI/브랜치 보호·작업 범위의 최소 syntax/type/smoke·고위험 권한/비밀/외부전송/원본·DB 손실/F18 관련 즉시 확인은 계속 유효. 이는 반복 종합 검수로 확대하지 않는다. 실제 원본/권한/고객 데이터/Production/외부 호출·유료 결제가 위험한 경우 해당 실행만 차단하고 독립 BE 코드 작업은 계속. 임의 CI 비활성화, 승인 없는 main 병합·배포/보안 설정 변경은 금지.
6. **작업당 상한:** SWU당 실제 기능 구현 1회 완료 후보를 목표. 동일 원인 초기 2회 무진전이면 SWU만 격리, 원인 재설계 후 추가 2회(총 최대 4회) 개선 시도. 여전히 실패하면 `SOLMAX_BATCH_PENDING` 배치 이관, 필수 차단은 즉시 `IMMEDIATE_OWNER_SOLMAX_REQUEST`. 다른 독립 READY 계속, `ㄱ`당 안전한 4~6개 구현 시도 목표(완료 보장 아님).
7. **증거·보고 최소화:** 코딩 회차 종료 때 `실제 구현 SWU ID/REQ / 수정 소스 경로 / 커밋 SHA / 국소 필수 검사 PASS·FAIL·NOT_RUN / P2 이관 / 차단·다음 READY / 구현완료율(근거 있는 경우)`만 기록. 코드 변경이 없으면 구현률 +0. `docs/STATUS/HANDOFF`는 실질 변경·인수인계 시 1회 갱신, 상태 불변 빈 커밋/장문 보고는 하지 않는다. 기존 28/15 작업은 최신 실제 코드 기준으로 재산정한다.

**강제 구분:** `P1=백엔드 우선 실제 기능 코딩(+설계상 필수 FE 코딩)` / `P2=검증·테스트·보안·브라우저·수정·재검증`. 이 규칙은 향후 모든 소프트웨어 개발 P1에 적용하되 별도 해총 GitHub App **운영 검증 임무를 BE 개발 임무로 바꾸지 않는다**.

## 0A. 2026-11-17 사용자 최종 정정 — P1은 실제 기능 코딩만, 기타 검증 작업 P2

**최우선 적용 규칙:** 앞으로 모든 개발 프로젝트의 P1 표준작업단위(SWU)는 **GPT-6 Sol High의 실제 BE/FE 기능 코드 작성·연결에 드는 작업량만** 대상으로 산정한다. P1의 목적은 코드로 필요한 기능을 구현하여 `IMPLEMENTATION_100_CANDIDATE`를 만드는 것이며, **검증 프로그램을 만드는 작업량이나 CI/보안/브라우저 테스트를 수행하는 작업량을 SWU에 섞지 않는다.** 사용자 명시 지시에 따라 이 절이 기존 본문에서 테스트 하네스·최소 검사·검증 산출물을 SWU 내용처럼 설명한 부분보다 우선한다.

| 항목 | P1 구현완료율: SWU 산정 대상 | P2 검증완료율: 별도 검증 큐 |

**P1 SWU의 완료 판단(코드 기준):** 기능의 입력·실제 caller→callee·출력/상태·주요 예외 처리 코드가 작성되어 기존 코드와 연결돼 있고, `REQ-ID + 소스 경로 + SHA + 남은 코드 간극`이 정리되면 **`IMPLEMENTED_UNVERIFIED` 후보**로 본다. 일반적인 검증의 미실시는 **P1 재작업 근거가 아니다**. `Preview`/`Intent`/모의 영수증만 연결한 상태나 TODO는 코드 미완성이므로 다음 코드 SWU에서 실제 동작 로직을 구현한다. 최종 기능/권리·고객 실사용은 아직 미승인이다.

**시도 규칙:** 1 SWU=웹 GPT-6 Sol High 실제 기능 코딩 1회 완료 목표. 무진전 초기 2회→격리/재설계→추가 개선 2회→총 4회 실패 시 Sol Max 일괄 이관; 필수불가결 차단은 즉시 사용자에게 Sol Max 요청. 다른 독립 READY 계속; 시도는 실제 코드·관찰 근거로만 계산. SWU S/C/I/D/U는 구현 코드 복잡도만 평가하고 P2 검증을 횟수/분모에 섞지 않는다.

**안전 조건(비우회):** 기존 필수 CI/브랜치 보호는 끄지 않는다. 원본 파일/DB·중요 브랜치·권한·인증·비밀·외부 전송에 실제 영향을 주는 코드의 **위험한 실행/활성화는 GO와 필요한 즉시 안전 확인 없이는 차단**한다. 해당 위험 경로는 `HOLD`로 두되 개발용 독립 코드 작성은 계속한다. 최소 syntax/type/smoke와 고위험 변경의 즉시 확인이 필수인 경우 이를 생략한다고 약속하지 않는다. **P2로 전체 검증을 미루는 것과 필수 안전장치를 제거하는 것은 서로 다르다.**

**P2 진입:** 프로젝트별 `P1 구현 후보 100% + High 인수/정확 SHA` 게이트 이후 Codex GPT-6.1 Sol Max가 전체 검사·테스트 작성·결함 수정·재검증을 묶어 수행한다. P2 검증 항목의 작업 분할·시도 예산에 P1 SWU 2+2 실패 처리 예산을 적용하지 않는다.

## 0. 최우선 범위 잠금 — SWU는 오직 P1 구현 작업의 표준

**사용자 2026-11-17 추가 확정:** 이 SWU 산정 기준은 MLA/EAI만의 특례나 일회성 재산정표가 아니라, **앞으로 모든 프로젝트에서 사용하는 P1 기능 구현 작업의 표준 단위**다. 모델 용량 기준은 항상 **웹 GPT-6 Sol High의 실제 기능 코드 작성 1회**이며, Instant 또는 Codex의 호출량/파일 수/테스트 작업량을 기준으로 단위를 정하지 않는다.

- **P1 SWU에 포함:** 승인된 최종설계의 실제 BE/FE/CLI/Controller/API/DB 코드, 의존성·인터페이스 연결, 필수 예외/실패 처리, 구현 확인에 필요한 최소 테스트 *코드 작성*, 정확 소스 SHA·변경 경로 및 완료/미완료 판정. 제품 기능의 실제 코드 경로가 연결되는 것이 목표다. 단순 Preview/Intent/mock-only/test-only 작업은 실제 기능 미구현을 대체하지 못한다.
- **P1 SWU 크기 산정에서 제외:** 전체 CI 실행/대기, 통합·종합 기능 E2E 실행, 브라우저·Playwright/화면·접근성·반응형 검증, 전체 보안감사/침투·회귀·복구 검증, Windows/모바일/실기기/실모델·24시간 실측, 사용자 검수와 운영 승인 등 **P2 검증완성률 단계의 실행·수용 작업**. 이것들은 **별도의 P2 검증 큐/수용 매트릭스**로 계획하며 SWU 개수·복잡도 점수·P1 완료 분자에 가산하지 않는다. 사용자 질문의 '모든 작업'은 **모든 P1 구현 작업**을 뜻하며 P2 검증 작업 크기까지 이 1 SWU로 강제하는 것이 아니다.
- **P1에도 그대로 남는 필수 최소 안전검사:** 소스 구문/타입/필수 최소 빌드·국소 smoke, 인증·인가/권한·비밀·외부전송·원본/DB 손실·신뢰 경계 등 변경 시 즉시 필요한 안전 확인, 기존 필수 자동 CI/브랜치 보호, 사용자 사전 GO. 이는 종합 P2 검증의 선행 대체가 **아니며** 무단 삭제·우회할 수 없다. 안전 확인 때문에 해당 코드 작업을 승인 없이 실행할 수 없다면 위험 경로만 HOLD하고 독립 SWU를 진행한다. 필수 최소 검사의 실행 수는 SWU 크기나 완료율 분자가 아니다.
- **상태:** 코드 구현 후보는 `IMPLEMENTED_UNVERIFIED`/구현완료율 후보, P2 항목은 `NOT_RUN/DEFERRED_TO_P2` 또는 근거 있는 `NOT_APPLICABLE`. P1 100% 후보가 검증 100%나 실사용 GO를 의미하지 않는다. REQ 분모와 승인 가중치, P2 단계 전환은 프로젝트 고유 게이트를 따른다.
- **향후 사용:** P0 High 최초 설계에서 모든 REQ를 SWU로 매핑하고 P1 작업 큐를 작성한다. P1 담당자가 `ㄱ`을 받으면 정본 SWU 큐의 독립 READY 4~6개를 묶어 실제 구현을 진행한다. P2 담당자는 **별도 검증 큐**를 실행하며, P2 항목을 SWU 재산정·작업당 시도 예산에 섞지 않는다. 기존 다른 제품의 작업 큐는 안전하게 확인·재산정·커밋할 때 실제 적용된 것으로 보고한다.

## 1. 표준의 기준 모델은 웹 GPT-6 Sol High다

**1 SWU = 웹 GPT-6 Sol High의 의미 있는 기능 코딩 1회에 실제 소스·호출 경로·주요 실패 처리까지 구현 완료 후보로 만들 수 있는 독립 수직 기능 단위.** 필수 국소 안전검사는 P1에서 보존하지만, 전체 검증을 SWU 작업 크기/완료조건에 섞지 않는다. 
- **한 번의 작업 회차**는 High가 진행하는 하나의 구현 라운드(필요한 여러 GitHub 읽기/편집 호출을 포함)이며, Git API 호출 1번/파일 1개/함수 1개/테스트 1개/고정 LOC·토큰·시간을 뜻하지 않는다.
- **한 번의 `ㄱ`**에서 충돌 없는 SWU를 4~6개 묶어 *시도할* 수 있다. 이것은 SWU당 허용 시도 횟수나 4~6개 완료 보장이 아니다. 병렬 구현의 담당 모델이 Instant여도 크기 산정 기준은 계속 웹 Sol High.
- REQ는 제품 **요구사항**, SWU는 **구현 용량**: 1 REQ가 여러 SWU를 필요로 하거나 SWU 하나가 여러 REQ의 같은 수직 호출 경로에 걸칠 수 있다. 둘의 개수를 맞추지 않는다. `기존 MLA 30 REQ/28 task`, `EAI V3 15 task group`은 출발 인벤토리일 뿐, 표준 산정 결과가 아니다.
- 검증전 `IMPLEMENTED_UNVERIFIED`는 해당 SWU의 코드 경로 완성을 뜻할 뿐 제품 운영·P2 검증 PASS가 아니다.

## 2. 작업 경계 — 무엇을 1 SWU에 담는가

**필수 5개 판정조건** (하나라도 누락되면 일반 SWU로 잡지 말고 재분해):
1. **명확한 관찰 가능 결과 한 가지:** `사용자/내부 caller 입력 → 기능 진입점(API/CLI/UI/Controller) → 실제 구현 모듈 → 기대 출력/저장된 상태`라는 한 개 end-to-end *코드 경로*. UI·DB·보안 모듈이라도 호출자와 결과가 명시되어야 한다.
2. **단일 책임 경계:** 새 공개 계약/핵심 API는 원칙적으로 1개 이하, 주요 상태 전이는 1개 이하, 새 독립 기능 도메인 1개. 불가피한 교차 레이어는 **같은 기능에 필요한** 연결만 포함한다. 파일·LOC 수로 나누지 않는다.
3. **의존성 검증:** 이미 존재하는 코드는 그대로 사용. 이전 SWU나 기존 안정 계약에 의존하되 **해결되지 않은 승인/보안/권리/OS 위험을 완성 판정 조건으로 숨기지 않는다**. 실실행 권한이 필요한 부분은 코드 작성과 별도 HOLD/GO로 분리한다. 외부/보호된 원본에 무단 쓰기는 금지.
4. **코딩 수용조건:** 변경된 실제 소스 파일/진입점/호출 연결, 정상 경로와 주요 실패 경로(안전 거부 포함), 국소 문법·타입·스모크/관련 보안 테스트, 수용 근거 exact SHA와 미실행 항목. 단순 `Preview`/`Intent`/TODO·스키마 문서·미연결 모듈·합성 테스트 수만으로 완료 불가.
5. **비중복성:** 기존 코드가 이미 수용조건의 전체 BE/FE 구현 경로를 갖췄다면 재코딩하지 않고 `SOURCE_COMPLETE_P2_PENDING` 후보로 식별. 부족한 **실제 caller→callee 마지막 간극**만 별도 SWU로 만든다. 보안 계약·HOLD 문구만 반복 강화하는 SWU 금지(새 결함/고위험 요구 근거는 예외).

## 3. 사전 스코어링 (High 1회 구현 가능성의 **초기 설계용** 휴리스틱)

각 후보 SWU는 5개 복잡도 축에 **0/1/2** 값을 기입하고, 추정 근거를 한 문장씩 쓴다. 이 점수는 구현완료율이 아니라 **작업 크기** 지표다.

| 축 | 0점 | 1점 | 2점 |
|---|---|---|---|
| **S 표면** | 하나의 기존 모듈/레이어 | 두 레이어 연결 | 셋 이상 레이어 또는 독립 도메인 결합 |
| **C 계약** | 기존 안정 계약 그대로 | 한 계약/모델 확장 | 여러 신규 계약·호환성/마이그레이션 |
| **I 통합** | 같은 프로세스 로컬 | 내부 API/DB/CLI 한 경계 | 복수 실행기/서브시스템·원격 연계 |
| **D 데이터·안전** | 무상태·읽기전용 | 자기 소유의 가역 상태 한 개 | 인증·원본/권한·교차 DB·서명·신뢰 경계 |
| **U 불확실성** | 소스·의존성·수용조건 명확 | 제한된 알려진 간극 1개 | 외부 승인/미정 설계·플랫폼 동작 미확인 |

**산정:**
- **0–3점: 표준 SWU (NORM)** → 웹 Sol High 의미 있는 기능 구현 1회 완료 후보 목표. 실패 때만 공통 §0C 2+2 단계 적용; 2회 무진전 즉시 격리.
- **4–5점: 과대 범위** → 우선 caller→callee·계약·상태 전이 경계로 2개 이상 SWU 분해. 안전하게 분할할 수 없는 경우 High가 `COMPLEX_EXCEPTION` 근거를 기록하되 실패 처리 예산은 동일한 §0C 2+2 규칙.
- **6–10점: 과대/고위험** → High 재설계·원자성 판단 필수. 승인·보안 경계를 우회해 작업 횟수를 채우지 않는다. `SPECIAL_MAX3`은 과거 방식이며 최신 실패 처리 규칙 §0C(2+2, 필수 즉시 요청)로 대체. 실운용은 승인 전 `BLOCKED_APPROVAL/HOLD`.
- **강제 예외:** D=2 또는 U=2면 총점이 낮아도 반드시 High/안전 검토·코드-only 경계 표시. 비밀·인증·원본·권한·외부 전송·결제·F18 관련 **즉시 안전검사는 P2로 미루지 않는다**. 운영 승인 없이 `실행 성공` 주장을 금지.
- 이 스코어는 정답이 아니라 **초기 용량 예측**이다. Web Sol High의 실제 코딩 회차 증거로 뒤에 캘리브레이션하되 코드 기준/안전 게이트를 소급 하향하지 않는다. 근거 없는 임의 시간·토큰·LOC 임계치 사용 금지.

## 4. 실행 예산과 완료 판정

- **정의:** `attempt`는 해당 SWU가 정한 결과를 만들기 위해 웹 Sol High가 실제 기능 소스 코딩/수정을 수행한 **의미 있는 한 구현 회차**. 같은 회차 내부 여러 편집/테스트·커밋 수를 따로 세지 않는다. 단순 `ㄱ` 입력·읽기·계획/문서만·CI polling은 시도 아님. 누적은 SWU 단위로 기록한다.
- **표준:** 1회 실제 기능 구현 완료 후보 목표. 원인별 개선 초기 최대 2회 실패 시 격리, 재설계 후 서로 다른 개선 추가 최대 2회. 총 4회 무진전은 `SOLMAX_BATCH_PENDING`, 필수 차단은 즉시 사용자 Sol Max 요청. 정상적인 실제 진전은 무진전 실패가 아니다.
- **격리 후 재시도:** 같은 원인으로 실제 2회 무진전이면 `ISOLATED_REDESIGN_PENDING`으로 해당 작업만 격리하고 독립 READY를 계속한다. 원인·방법 변경의 증거 확보 시 추가 2회, 그래도 실패하면 Sol Max 배치 이관. 위험한 실행·안전 실패·필수 차단은 횟수와 무관하게 즉시 중지·승인 또는 Sol Max 요청.
- **SOURCE_COMPLETE_P2_PENDING:** 실제 코드 경로·최소 필수 검사 및 근거가 있지만 P2 검증이 남은 상태. **별도 `IMPLEMENTED_UNVERIFIED`** 등 프로젝트 원래 상태·공식 REQ 기준과 함께 기록; `VERIFIED`로 오인 금지.
- **코드 미완성:** `PARTIAL_SOURCE`, `BLOCKED_CONTRACT`, `BLOCKED_APPROVAL`, `HOLD`로 구분. HOLD의 이유를 제거하지 않고 별개 코드-only SWU를 만드는 건 가능하나, 실운용 권한을 해제한 것이 아님.
- **반복 방지:** 기존 SWU를 분리·합치더라도 이전 시도 횟수/실패 증거와 소스 SHA를 **새 ID의 `supersedes`/legacy mapping에 승계**한다. ID 교체만으로 예산 리셋·가짜 진행률 증가 금지.

## 5. MLA·EAI 재산정 작업 산출물 (담당 개발자에게 지시)

1. **최초 조사:** 각자 GitHub 정확 `repo@branch@HEAD`, AGENTS/HANDOFF/STATUS, 요구사항/확정 최종설계, 현재 실제 코드·caller 연결, 현행 큐/수용조건, 기존 미실행 테스트 및 blocker를 읽는다. **MLA는 최신 28 작업/30 REQ**, **EAI는 현재 15 작업군**의 전체 항목을 빠짐없이 매핑. EAI 고유 Architect/Player/AXNODE와 MLA 고유 Controller 분리.
2. **전수 교차표:** `legacy_task_id | req_ids | actual_source_paths | caller_to_callee | missing_function | code_status | safety_blockers | score_S_C_I_D_U | total | proposed_swu_id | predecessor_swu_ids | max_attempts | current_attempts | evidence_sha`. 기존 실제 소스가 있는 작업의 기능 완료 여부를 구체적으로 진단. 확정된 REQ 분모를 함부로 변경하지 않는다.
3. **새 SWU 리스트:** 위 표로 기존 과대 작업은 나누고 중복 단위는 결합/제거하되 **REQ 범위/실제 기능은 삭제 금지**. 모든 새 SWU는 단일 결과, 정확 `allowed_paths`, 코드용 선행조건, 전체 운영/권리/보안용 선행조건, 국소 수용조건, P2 후행 검증, 우선순위/차단/attempt 현황을 포함. 최종 작업 건수는 **근거 기반으로만 결정**하며 28/15/30에 맞추지 않는다.
4. **검토와 파일 변경:** 기존 정본 작업 큐/Runbook/PHASE GATE를 **최소 변경**하는 `재산정안`부터 산출하고 High가 승인된 설계 범위·D=2/U=2 안전을 검토한 뒤 큐에 반영한다. 각 프로젝트의 사용자 확정 FINAL BLUEPRINT/REQ-ID, 원본·코드/테스트, 현재 안전 게이트·P2 LOCK은 **절대 덮어쓰지 않는다**. 큐 변경이 런타임 허용으로 이어지지 않게 별도 코드-only/실운영 상태를 보존.
5. **실행계획/증거:** 재산정 전후 `legacy_task_count → SWU_count`, 점수 분포 및 분할 근거, 남은 실제 코딩 간극, 첫 독립 READY 4~6개, 초기 2회·격리 후 2회 실패 처리 분포, 도중 실패 HOLD 정책, 실제 repo@branch@SHA 및 P1/P2 분리. **실제 개발코드가 변경되지 않았다면 구현 진척 변화 0**, P2 UNASSESSED 유지. 다른 모델/채팅에게 문서를 직접 보냈다는 주장보다 GitHub branch 파일/Issue와 실제 SHA를 증거로 사용한다.

## 6. 우선순위/금지

- 본 기준은 **웹 GPT-6 Sol High의 생산능력에 맞춰 산정**한다. 하위 담당자인 웹 Instant의 생산속도를 기준으로 작업단위를 잘게 나누거나 과대하게 잡지 않는다. Instant는 승인된 SWU 실행 구현 담당자로 참여할 수 있다.
- 기존 필수 CI, 보안·데이터 손실/권한·원본 보호, F18 독립 검증, owner GO, 단계 분리(P1 코드 / P2 전체 검증), 운영/고객 승인, Git history 보호는 유효.
- `ㄱ` 주 임무 잠금: 해총 채팅 단독 `ㄱ`은 GitHub App→HMAC Webhook→Vercel→Actions→중앙 원장. 이번에는 사용자가 **MLA/EAI 공통 설계 재산정 지시를 명시**했으므로 이 예외적 정책 배포는 허용됐지만 다른 코드/배포/원장 변경 자동 허가는 아님.


## 사용자 지정 Sol Max 요청 경로 선택 (2026-11-17 KST)

- **요청 책임:** 실제 SWU를 수행 중인 해당 제품 개발 작업자. 해총은 공통 정책만 유지한다.
- **Codex**: 소스/기술 설계/코드 결함 재현과 수정, 보안·F18 신뢰 경계, CI/테스트/PR 기반 코드 검수. 작업 원본은 정확 branch/SHA로 고정한다.
- **ChatGPT Work**: 소유자 승인 범위의 실제 브라우저/로그인·GitHub/Vercel 콘솔·외부 서비스 UI·멀티스텝 현장 조사/검증. Work 실행 자체를 Codex GPT-6.1 Sol Max 실행으로 오인하지 않는다. 모델 가용성은 별도 확인, 불확실하면 `MODEL_UNVERIFIED`.
- **혼합 사례**: 코드 수정을 Codex 1차, 브라우저 재현/실검증을 Work 2차처럼 범위와 검증 책임을 분리. 필요없는 양쪽 동시 요청 금지.
- **사용자 요청 형식(필수):** `요청자=제품 실작업자; 장애종류=즉시 필수 차단|2+2 일괄; 실행수단=Codex|Work; 선택 근거; 모델=실제 사용 가능/미확인; repo@branch@SHA; SWU/REQ; 이전 실패 0–4회 증거; 요청 작업/수용기준; allowed_paths; 비용/원본/권한/Production 사전 승인 필요 여부; 다른 READY 진행 여부`.
- **절대 금지:** 모델 실행 여부 과장, 자동 사용자 GO, F18/원본/인증/비밀/Production/필수 CI 우회, 정책 변경을 제품 구현 진척으로 산정.
