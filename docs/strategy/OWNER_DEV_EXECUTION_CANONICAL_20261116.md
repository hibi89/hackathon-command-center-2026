## 0B. 브라우저 검증 후행·외출 중 무중단 구현 정책 (2026-11-17 사용자 확정)

P1에서 브라우저를 돌리지 않았다는 이유만으로 완료된 구현 코드의 REQ 진척을 취소하지 않는다. **그러나 코드·API 연결·FE 사용자 흐름 자체가 미구현이면 해당 REQ 완료로 계산하지 않는다.**

**외출/모바일 무중단 규칙:** P1 작업자가 브라우저 인증, OTP, CAPTCHA, 로그인 재승인, UI/화면 공유, PC 조작, 외부 계정 접근권, 실기기, 클라우드 서비스 권한을 요구하는 **검증 전용** 단계에 도달하면 그 검증을 `DEFERRED_TO_P2`로 분리하여 P1 큐에 종속시키지 않는다. 실제 수행하지 않은 항목은 `NOT_RUN`이다. 불필요하게 사용자에게 승인 요청을 반복하지 말고 외부 의존성 없는 다른 독립 READY 구현을 즉시 계속한다. 토큰·세션·권한 우회, 자동 로그인·보안 승인 대리, 허위 PASS는 금지한다.

**P2 실제 실행:** P1 100% 구현 후보 + 정확 SHA + High 인수 게이트 후 Codex Sol Max가 전체 CI/통합/보안·실제 브라우저/Playwright/E2E/UX·실기기 검증을 묶어 수행하고 결함 수정과 영향 범위 재검증을 진행한다. Astra의 FE 변경에 대한 브라우저·반응형·접근성 재검증은 해당 SHA에서 후행 적용한다. 브라우저를 사용할 수 없으면 `NOT_RUN/BLOCKED`, 브라우저 비대상 CLI/오프라인 처리기는 근거 있는 `NOT_APPLICABLE`; HTTP/정적검사만으로 브라우저 PASS 주장 금지.

**불변:** 기존 필수 GitHub CI/브랜치 보호를 끄거나 우회하지 않는다. 새 퍼센트 지표·가중치/분모·승인 REQ를 임의 변경하지 않는다. 해총 `ㄱ` 주 임무는 여전히 GitHub App→HMAC→Vercel→Actions→중앙 원장이고, 이 정책은 중앙 관리 제품의 개발 방식에만 적용한다. 각 원본 저장소/브랜치에 자동 적용된 것으로 주장하지 않는다.

## 0C. 병목 감지 → 작업 설계 최적화 → 실제 구현 재개 (2026-11-17 사용자 확정)

**핵심 계약:** P1 작업자가 장애·비효율·중복 대기·의존성 교착을 발견하면 같은 실패 경로를 반복하거나 상태보고만 하지 않는다. 기존 최종설계/REQ 수용범위는 고정한 채 **진단 → 실행 설계/작업 큐 재편 → 개선된 방법 1회 시도 → 독립 READY 병렬/묶음 구현 → 실제 증거 기록**을 같은 작업 회차에서 수행한다. `ㄱ`/`ㄱㄱ`도 현재 채팅의 **잠긴 임무**를 벗어나지 않는다. 설계의 핵심 계약·제품 범위 변경이나 보안/운영 위험은 High/소유자 승인 게이트를 통과해야 한다.

1. **병목 트리거/계측:** 동일 원인의 오류·재시도, 재현 불가 환경/브라우저/OTP, 장시간 CI 대기, 느린 도구 왕복/순차 파일 수정, READY 의존성 교착, 외부 사용량·토큰·비용 한도, 브랜치 충돌, 테스트 하네스 부족을 병목 후보로 인식한다. `repo@branch@정확 SHA / task_id / 로그·응답 / 경과·호출 수 / blocked_by`를 확보하고 **실제 진척이 있는 긴 작업과 진척 없는 반복 실패는 구별**한다.
2. **원인별 빠른 분기:** (a) **구현·코드 결함**은 최소 재현→국소 수정/타입·스모크 확인, (b) **큐·설계 의존성/효율 문제**는 REQ 유지 조건으로 작업 순서/인터페이스/파일 소유권을 재배치하고 중복 조회·문서 왕복 축소, (c) **외부 계정·브라우저·실기기·한도**는 P2 검증 전용이면 `DEFERRED_TO_P2 / NOT_RUN` 격리, (d) **보안·데이터·인증·권한·필수 CI**는 필수 안전검사가 불가능하면 해당 위험 작업만 `HOLD`, (e) **GitHub HEAD·충돌·도구 권한**은 원본/HEAD 재조회 후 최소 변경·안전한 재기준화. 허위 PASS나 우회는 금지.
3. **실행 설계 재구성:** 가능한 해결안 중 최소 **2가지 경로를 속도/호출·비용/안전/유지보수로 내부 비교**하여 승인 범위 내 최소 위험안을 선택한다. 기존 `INSTANT_TASK_QUEUE`/`INSTANT_RUNBOOK`의 `task_id, req_ids, depends_on, allowed_paths, implementation_acceptance, minimal_safety_checks, risk, status, evidence_sha, blockers`를 갱신한다. 차단된 과제는 `BLOCKED_EXTERNAL`/`HOLD`, 독립 기능은 `READY`; 이미 끝난 과제를 되돌려 새 진척으로 세거나 임의 분모·가중치·기능을 삭제하지 않는다. 기존 정본이 있으면 신규 정본 중복 생성 금지.
4. **개선된 방법으로 1회 재시도:** 오류 분석 없이 동일 명령·동일 승인 팝업·동일 CI 조회 반복 금지. **진전 없는 동일 문제 2회 실패**면 해당 경로를 중단·원인/대안/요청사항 기록 후 High 설계 판단 또는 외부 승인 게이트로 이관한다. **정상적인 실제 코드 진전은 횟수 제한 대상 아님.** 차단 작업 하나 때문에 전체 구현을 멈추지 않는다.
5. **재개 및 처리량 최적화:** 충돌하지 않는 `READY` 3~10개(가능할 때)를 REQ 의존성과 허용 파일 경로로 묶어 **같은 회차에 실제 BE/FE 코드 작성·커밋**한다. 빈 커밋/상태 확인만 반복하지 않는다. P1 전체 CI·브라우저/Playwright E2E·시각/반응형/a11y 실행은 후행 P2로 보낸다. 문법·타입·변경 국소 스모크, 필수 CI 및 고위험 즉시 안전검사는 유지한다. 불필요한 호출/중복 검증을 줄이되 회귀·복구 게이트를 삭제하지 않는다.
6. **완료 근거 및 다음 작업:** 매 회차 `repo / branch / 정확 SHA / 수정 경로 / 처리 REQ-ID / 구현완료율 전→후(분모 미확정이면 UNASSESSED) / 실행 검사 PASS·FAIL·SKIP·NOT_RUN / P2 이관 / 남은 병목·다음 READY`를 간결하게 기록한다. **코드 없는 정책/문서 수정은 실제 제품 구현 진척 0**으로 표시하며, 코드 작성·검증·커밋이 없으면 '작업 재개 성공'이라 주장하지 않는다. 실제 브라우저 미실행은 검증완료율에도 PASS로 반영하지 않는다.

**권한·안전 불변:** 사용자 승인 없는 최종설계 범위 축소·중대한 아키텍처 변경, DB 파괴, 고객 원본/비밀의 공개 이동, 유료 결제, GitHub 권한/필수 CI·브랜치 보호 변경, Production 변경, main 병합, 상용 출시를 최적화 명목으로 시행하지 않는다. 이 조항은 **중앙 실행 정책**이며 개별 제품 저장소의 큐/코드가 자동 변경된 것으로 간주하지 않는다.

## 0D. 2026-11-17 사용자 확정 — 작업당 1회 완성 목표·최대 3회·`ㄱ` 4~6개 실제 기능 묶음 (MLA 병목 개선안 공통화)

> **새 실행 규칙:** 기존 0A~0C의 구현/검증 분리와 재계획·고위험 안전 게이트를 **강화**한다. 과거 작업마다 HOLD/Preview/Intent/합성 테스트만 누적하는 방법은 **실제 구현 진척을 입증하지 못한다**. 현행 최종설계 범위, 제품별 REQ 분모, 프로젝트 고유 권한·실행·보안·비용/권리 제한은 그대로 유지한다.

### 문제의 정확한 구분
- 사용자가 MLA를 검토하며 지적한 **28개 작업에 코드 증거가 있더라도 실제 기능 REQ 30개가 완료된 것은 아니라는 현상**을 일반적인 개발 반면교사로 사용한다. 이 숫자를 다른 제품의 task/REQ 분모로 복사하거나 EAI/해총 진척률로 주장하지 않는다.
- `Preview`, `Intent`, 합성 테스트, task별 `evidence_sha`, 문서상 READY 회전은 **필요한 일부 소스 증거**일 수 있으나 Controller/호출자→실행자/실제 DB·API·FE 연결 등이 빠지면 REQ 구현완료로 계산하지 않는다. 같은 권한 HOLD 계약·안전 문구만 반복 보강하는 것은 일반 P1 진척 우선순위가 아니다.
- **P1은 미구현된 전체 실행 경로의 BE/FE 코드를 실제로 작성하는 단계**이다. 그렇다고 실제 보호된 Git/OS/원본·고객 데이터/외부 전송/실서비스 실행이 허가된 것은 아니다. 코드 구현·국소 안전검사와 운영 GO/전체 수용 테스트는 계속 구별한다.

### 실무 실행 계약
1. **기존 소스부터 REQ/호출 경로 감사:** 실 작업 시작 시 현재 `repo/branch/HEAD`, AGENTS/HANDOFF/STATUS, 확정설계·작업 큐를 확인한 뒤 각각 `REQ-ID → 남은 필수 기능 → caller/callee 연결 → allowed_paths → 수용조건 → source SHA`를 매핑한다. 이미 구현된 모듈·합성 테스트를 반복 생성하지 않고, 먼저 **미완성 기능·실제 연결 경로**를 완성한다.
2. **작업당 1회 완성 목표:** 일반 BE/FE 기능은 의미 있는 최초 구현 **1회**, 복잡한 연결은 최대 **2회**, 고난도 구조·위험은 **High 검토 후 최대 3회**만 시도한다. `attempt`는 구체적인 기능 완료를 위해 수행한 **실제 코드 구현/수정 시도**다. 사용자 `ㄱ` 입력·서류/코드 조회·CI 실행/조회·커밋 수를 시도 횟수로 대체하지 않는다. 진전이 있는 정상 개발은 동일 원인 실패로 취급하지 않는다.
3. **두 번 무진전이면 즉시 전환:** 같은 실패 원인이 진전 없이 2회 반복되면 세 번째 시도를 낭비하지 않고 `HOLD/NEEDS_HIGH`로 격리한다. 예외 허용 최대 시도 횟수 도달 후 미완료여도 해당 작업 HOLD. `task_id/req_ids/시도 근거/원인/후보 대안/blocked_by`를 남기고 독립 READY로 이동한다. 보안·권한·원본 손실·필수 CI·서명 독립성·승인 게이트는 횟수 제한을 근거로 절대 생략하지 않는다.
4. **`ㄱ` 한 회차에 4~6개 독립 작업을 구현 목표로:** 충돌 없는 READY 4~6개(현행 큐에 충분하지 않거나 위험하면 가능한 수만)를 동시 준비/묶음 코드·테스트 작성·커밋한다. 의존/allowed_paths가 겹치면 순서 조정. 문서·HOLD만 추가하다 회차를 끝내는 방식은 지양한다. 횟수 목표는 SLA나 강제 100% 완료 보장이 아니다.
5. **P1→P2 판정:** 각각의 완료 판정은 실제 BE/FE/CLI/DB/API 소스+연결 경로+REQ 수용에 필요한 **코드가 완성됐는지**로 한다. P1 국소 문법/타입/필수 최소 빌드·스모크 및 인증/인가/비밀/권한/외부전송/원본·DB 손실 관련 즉시검사는 유지. 브라우저·Playwright/전체 CI 반복 대기·실기기/전체 보안·회귀·UX는 P2로 이관(`NOT_RUN/DEFERRED_TO_P2`). 기존 필수 자동 CI와 브랜치 보호는 비활성화하지 않는다. 코드 완성 후보는 `IMPLEMENTED_UNVERIFIED`, 실행 수용 증거가 있을 때만 `VERIFIED`.
6. **진척 보고:** `repo@branch@SHA | 실제 구현 충족 REQ/전체 또는 UNASSESSED | 새 기능·소스 경로·호출 연결 | task별 의미 있는 attempts | 국소 PASS/FAIL/SKIP/NOT_RUN | P2 UNASSESSED/LOCKED | HOLD·다음 READY`. task source 증거 개수/합성 테스트 수/파일 수만으로 구현완료율을 가산하지 않는다. P1 코드가 없고 정책 문서만 변경된 회차는 제품 구현 진척 **0**이다.

### 원본 보존과 적용 범위

- P1에서 제외하면 안 되는 것: 기존 필수 자동 CI와 브랜치 보호 유지, 실제 소스 작성에 필요한 최소 문법·타입·스모크 확인, 인증/인가·비밀·권한·원본/DB 손실·외부송신·F18 등 고위험 변경의 즉시 필수 안전 확인, 위험한 실실행·배포/권한 변경에 대한 사전 GO. 위험 변경이 안전 확인 없이 실행될 상황이면 **해당 작업만 HOLD**하고 독립 P1 READY 코딩을 계속한다. 최소 검사의 횟수/시간으로 SWU 크기를 늘리거나 P1 점수를 산정하지 않는다.
- 사용법: 1 SWU = **웹 GPT-6 Sol High의 의미 있는 실제 구현 1회 코드 완성 후보 크기**. 일반 1회 목표·최대 2회, High 판단 특수 최대 3회; 같은 원인 무진전 2회면 HOLD. `ㄱ` 한 회차에 독립 SWU 4–6개 코딩 시도. 검사/검증/문서 묶음은 SWU로 분할하지 않는다.
- 기존 제품 SWU 재산정안, 해총 `AGENTS.md`, MLA/EAI 담당 Issue는 별도 정확 SHA로 반영한다. 이 문서만으로 다른 저장소가 자동 동기화되거나 기능 구현이 진행된 것은 아니다. 해총 단독 `ㄱ`은 기존 GitHub App 중앙 자동화 임무로 잠근다.

## 0. 권위의 계층 및 상충 해소
1. **실시간 사용자 명시 지시, 비용·보안·권한·원본·출시의 사용자 사전 승인 조건**이 최우선이다. 같은 층위의 지시가 충돌하면 최신의 명시 지시를 채택한다.
2. 각 프로젝트의 **최신 사용자 확정 최종설계·REQUIREMENTS·승인 가중치**는 기능 범위와 수용 기준의 정본이다. 이 공통 문서는 전체 기능을 축소하지 않는다.
3. **개발 방식·모델 역할·검증 시점에 대해서는 본 `OWNER-DEV-EXECUTION-V2.1`이** 2026-11-14 GPT-only 단계 순서, 2026-10-28의 '활성 네 슬롯 이외 대기', '모든 작업마다 전체 CI', 'High가 구현도 독점' 등 과거의 상충하는 일반 운영방식보다 우선한다.
4. 프로젝트 `AGENTS.md`는 해당 저장소 고유 보안·데이터 보존·개발 분기·로컬/실환경 수용 조건을 추가한다. 공통 정책의 순서와 상충하는 **오래된 일반 실행 순서만 무효**, 제품 고유 안전/승인/상용 요구는 유지.
5. `HANDOFF.md`, `STATUS.md`, `CHAT_BOOTSTRAP.md`, `NEXT_TASK.md`의 과거 내용은 증거·연혁이다. 새 실행 책임을 배정하는 권한이 없다. 파일 첫머리에 '이 정책 우선' 안내가 있으면 먼저 그 정책을 읽는다.
6. **실제 코드/정확 SHA/테스트/최신 브랜치 증거는 진척과 결함 판정에서 문서의 추정 수치에 우선**한다. 임의 완성률 가점·검증 없는 '100%' 금지.

## 1. 사용자 확정 7단계 업무 순서 — 모델별 고정 책임

- **P0 최초 설계 — 웹 GPT-6 Sol High:** 최신 HEAD·최종설계·REQ-ID 전수/BE·FE·DB/API·인증·보안·비용·대안 비교·실행 큐·수용 매트릭스 최초 확정.
- **P1 기능 구현 후보 100% — 현재 웹 GPT-6 Sol High, 추후 웹 GPT-6 Sol Instant:** 승인된 범위에서 BE/FE 실제 구현·커밋. P1 퍼센트는 **CI·종합 검증 직전의 구현 완성률**에만 적용한다. 독립 READY 묶음 실행, 전체 CI를 매 커밋 수동 대기하지 않음(필수 자동 CI와 안전검사 유지). 고위험 구조 변경은 High 결정.
- **P2 전체 CI 및 검증·수정 — Codex GPT-6.1 Sol Max:** P1 구현 후보 뒤 전체 CI·빌드·통합·회귀·보안·복구·기능/실환경 검증을 묶고 결함 수정·재검증. **검증 완성률은 이 단계에서만 사용**하며 완료/미검증의 증거 SHA를 남김. Codex에게 소스/요구사항/수용조건을 전달하되 실행되지 않은 테스트를 PASS로 취급하지 않음.
- **P3 프론트엔드 끝판왕 실제 구현 — Codex Astra Max:** 검증된 BE/API/기존 기능을 보존하면서 화면·디자인·반응형·접근성·사용 흐름을 최고 수준으로 실제 코딩·커밋. 디자인 제안이나 단순 독립 검수만으로 완료 표시 금지.
- **P4 최종 코딩·보안 검수 — Codex GPT-6.1 Sol Max:** Astra 변경까지 포함한 정확 SHA의 전체 코드·인증/데이터·권한·보안·회귀·기능 연계 검수, 발견 결함 수정, 영향받는 테스트 재실행. **새 완성률 지표를 만들지 않고 PASS/FAIL/HOLD/미검증으로 보고**. P2 자신이 수정한 코드와 별도 감사의 독립성은 보장된 별도 검수 절차/세션에서 확인.
- **P5 최종설계도·누락 인수 — 웹 GPT-6 Sol High:** REQ-ID·BE/FE·운영·권리·고객/실기기 수용조건 전체와 실제 코드/CI/감사 결과를 대조, 누락 및 BLOCKER/HIGH 판단·인수. 중복 전체 CI를 무의미하게 반복하지 않으며, 상용 승인이나 100% 수치를 임의로 선언하지 않음.
- **P6 사용자 최종 상품화 승인 후 — Codex GPT-6 Luna Extra High:** 기존 19 SKU/중복·등록 이력 확인, 자료 준비 및 사용자 GO 범위에서 크몽 등록 실행. 실제 게시 URL/일자/증거 없으면 `등록완료` 금지. AX Dev Factory 같은 개인용 도구는 이 등록 단계 비적용.

이 순서가 구형 `Instant P2 검증`, `Astra 단순 UI 검수`, `Codex 1회 독립감사`, `High 매단계 전체 검증` 일반 절차보다 우선한다. 보안과 고유 프로젝트 승인 조건은 우선순위 변경으로 완화되지 않는다.

## 2. Instant 실행을 위한 최소 파일/상태 계약
각 제품의 **확정 설계 정본이 이미 있으면 중복하지 말고 참조**한다.
- 작업 큐 예시 `docs/INSTANT_TASK_QUEUE.json`: 각 `task_id / req_ids / depends_on / allowed_paths / implementation_acceptance / minimal_safety_checks / risk / owner / status / evidence_sha / blockers`.
- `docs/INSTANT_RUNBOOK.md`: `ㄱ` 단일 실행에서 READY 선택→코드 작성→부분 안전검사→SHA 커밋→다음 READY. 교착/고위험은 격리 후 독립 작업으로 이동, 재개 가능한 정확 stop point 유지.
- `docs/ACCEPTANCE_MATRIX.md`: **구현 완성률과 Codex P2 검증 완성률 두 개만** 운영한다. 구현 코드 근거/REQ-ID 및 P2 정확 SHA별 PASS/FAIL/SKIP/NOT_RUN을 추적한다. 가중치/분모 미확정 시 `UNASSESSED`; 출시·고객·OS·상품화 승인 등은 비율 없이 별도 게이트 상태로 기록.
- **1회 실행은 가능 작업을 묶어 최대 처리량을 목표**로 하지만 임의 1%p 보증/기한 보장은 금지. `IMPLEMENTED_UNVERIFIED`는 실제 기능 증명이 아니다.
- 실행 로그: `repo@branch@SHA | 구현 완성률(전→후 또는 UNASSESSED) | P2 검증 완성률(완료/전체 또는 UNASSESSED) | 테스트 PASS/FAIL/SKIP/NOT_RUN | P3~P6 상태(비율 없음) | 차단 | 다음 READY`. 이미 검증한 사실 반복 조사 금지.

## 3. 새 채팅/모델 전환 부트스트랩
1. **역할을 먼저 고정**: 중앙 해총 채팅인지, 특정 제품 개발/독립 검수인지, 개별 해커톤인지. 단순 `ㄱ`은 **현재 채팅/명시된 저장소의 잠긴 미션만** 재개하고 자동으로 다른 레포를 작업하지 않는다.
2. **대상 repo/branch/SHA의 HEAD를 우선 확인**, `AGENTS.md`의 최신 정책 배너를 먼저 읽어 우선순위를 확정. 종전 복원 흐름 `HANDOFF → STATUS → AGENTS → REQUIREMENTS → 최종설계 → 실제 코드`는 **자료 검토 순서**로 유효하지만, 먼저 읽힌 HANDOFF의 구형 작업 지시가 최신 AGENTS와 본 정책을 덮어쓰지 못한다.
3. `HANDOFF`의 가장 최근 유효 항목과 `STATUS`로 완료/차단/중단 지점 확인, REQUIREMENTS/확정 설계와 소스/테스트 교차 검증. 과거 추정치와 code HEAD가 다르면 실제 SHA·실행 결과를 우선, 차이를 기록.
4. 제품별 작업 큐와 담당 소유 파일/PR 확인 후, Instant는 기계적으로 다음 안전한 READY를 구현한다. 설계 큐가 없거나 100% 범위 미확정이면 **High 설계부터** 실시. 사용자 승인 없이 임의 큐를 만들어 전체 설계를 축소하지 않는다.
5. CI/외부 승인/실기기 장벽을 `BLOCKED_EXTERNAL`로 격리. 재시도 1회에서 개선되지 않으면 HOLD; 다른 독립 작업 계속. 완료시 STATUS/HANDOFF에 **정확 SHA·검증/미검증·다음 단위** 갱신.

## 5. 중앙 적용 증거와 한계
- 이 V2.1은 기존 중앙 V2 문서의 **동일 경로 정본 개정**이다. AX Dev Factory 시범의 실제 구현/P2 경험을 반영한 정책이지만 **다른 제품 브랜치의 자동 반영·실제 검증 성공을 의미하지 않는다**. 과거 P2/P3/완성률 설명은 이 문서의 상단 두 지표·7단계가 우선한다.
- 이 문서에 링크한 각 레포/브랜치가 **실제로 수정된 사실은 해당 GitHub 브랜치의 exact SHA 확인이 있어야만 APPLIED**. 중앙 링크나 과거 35repo/80ref 관찰 수치는 원격 전파 증거가 아님.
- 지침 충돌 해소는 최신 문서에 **효력상 우선순위를 명시**하는 방식으로 진행한다. 오래된 기록은 별도로 역사로 남기고 안전 조건은 삭제하지 않는다.
- ChatGPT/Codex **사용자 계정의 글로벌 Custom Instructions 및 로컬 `~/.codex/AGENTS.md`/설정 파일은 GitHub 커넥터로 수정할 수 없다**. 사용자가 해당 UI/로컬에서 최신 정책 붙여넣어야 한다. 편집 가능 여부를 확인하지 않은 상태에서 자동 적용 성공으로 보고하지 않는다.
- 별도 비용/배포/워크플로 권한·보안 변경, 고객 원본 변조, 오래된 CI 이력 재기록, 상품 출시 자동화는 이 문서의 범위 밖이다.
