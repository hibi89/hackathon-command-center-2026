- **실패 처리 별도:** 일반 SWU는 첫 2회의 근거 있는 무진전 실패→해당 SWU만 격리·원인 재설계→방법이 다른 추가 2회→4회 무진전 시 `SOLMAX_BATCH_PENDING`; 필수 임계 차단이면 0회 실패라도 즉시 담당 제품 작업자가 사용자에게 요청(`IMMEDIATE_OWNER_SOLMAX_REQUEST`). 사전 Sol Max 배정은 일반 실패 카운트 0회를 2/4회로 위조하지 않는다.

## 0A. 사용자 확정 완성률 개념 — 오직 두 가지 (최신 지시, 2026-11-16 KST)

**이 정책 적용 후 진행을 퍼센트로 표기할 때는 다음 두 명칭만 사용한다.** 기존 `최종완성률`, `실사용 완성률`, `상품화 완성률`, `출시 완성률`, `디자인 완성률`, 구형 70/85/95/100점은 현행 퍼센트로 사용하지 않는다. 예전 수치와 등록 기록은 역사/원장으로만 보존하며 임의 재계산·삭제하지 않는다.

1. **구현 완성률 (Implementation Completion):** 사용자 확정 최종설계의 백엔드·프론트엔드 필수 **기능 코드 구현이 전체 CI 및 종합 검증에 들어가기 직전까지 얼마나 끝났는지**만 측정한다. **브라우저/Playwright/E2E·클릭/시각·반응형/접근성 등의 실제 실행 검증은 P1 구현완료율의 분자·완료 조건에서 명시적으로 제외하며 P2 검증완료율에만 산입한다.** 해당 설계의 모든 요구사항 코드·연결·사용 흐름이 구현되어 `IMPLEMENTATION_100_CANDIDATE`가 되었을 때 **100%**. 100%는 CI PASS, 보안검수 완료, 작동 입증, 출시 승인을 **뜻하지 않는다**. 코드 존재만으로 기능 미구현을 완료로 바꾸지 말고 REQ-ID/소스경로/커밋으로 근거를 남긴다. P2 이후 구현 %를 새로 올리는 별도 목표로 삼지 않는다.
2. **검증 완성률 (Validation Completion):** **Codex GPT-6.1 Sol Max가 P2에서 수행하는 전체 CI·빌드·테스트·기능/통합·회귀·보안·복구 및 적용 가능한 브라우저·OS·실기기/실환경 수용조건 검증의 완료 정도**만 측정한다. 정확 소스 SHA와 사전 확정 수용 매트릭스에서 객관적으로 PASS한 항목만 반영하며 FAIL, SKIP, NOT_RUN, BLOCKED는 완료로 인정하지 않는다. 필수 전체 수용조건이 PASS했을 때만 **100%**. 검증되지 않은 외부/실기기 항목이 남으면 100% 금지. 전체 분모/가중치가 확정되지 않으면 % 대신 `UNASSESSED` 및 `통과 항목/전체 항목` 수를 보고한다. 단순 테스트 케이스 PASS 비율을 이 지표로 오인하지 않는다.

4. **즉시 안전 검사는 예외 없이 유지:** P1 중에도 문법·타입/국소 스모크 및 인증·시크릿·외부 송신·원본/DB 손실·권한·필수 CI/브랜치 보호 관련 안전 게이트는 생략하지 않는다. 상용/배포/권한/결제/실고객 자료 관련 사전 사용자 GO는 퍼센트와 별도로 유지.

P1에서 브라우저를 돌리지 않았다는 이유만으로 완료된 구현 코드의 REQ 진척을 취소하지 않는다. **그러나 코드·API 연결·FE 사용자 흐름 자체가 미구현이면 해당 REQ 완료로 계산하지 않는다.**

Astra의 FE 변경에 대한 브라우저·반응형·접근성 재검증은 해당 SHA에서 후행 적용한다. 브라우저를 사용할 수 없으면 `NOT_RUN/BLOCKED`, 브라우저 비대상 CLI/오프라인 처리기는 근거 있는 `NOT_APPLICABLE`; HTTP/정적검사만으로 브라우저 PASS 주장 금지.

**불변:** 기존 필수 GitHub CI/브랜치 보호를 끄거나 우회하지 않는다. 새 퍼센트 지표·가중치/분모·승인 REQ를 임의 변경하지 않는다. 해총 `ㄱ` 주 임무는 여전히 GitHub App→HMAC→Vercel→Actions→중앙 원장이고, 이 정책은 중앙 관리 제품의 개발 방식에만 적용한다. 각 원본 저장소/브랜치에 자동 적용된 것으로 주장하지 않는다.

2. **원인별 빠른 분기:** (a) **구현·코드 결함**은 최소 재현→국소 수정/타입·스모크 확인, (b) **큐·설계 의존성/효율 문제**는 REQ 유지 조건으로 작업 순서/인터페이스/파일 소유권을 재배치하고 중복 조회·문서 왕복 축소, (c) **외부 계정·브라우저·실기기·한도**는 P2 검증 전용이면 `DEFERRED_TO_P2 / NOT_RUN` 격리, (d) **보안·데이터·인증·권한·필수 CI**는 필수 안전검사가 불가능하면 해당 위험 작업만 `HOLD`, (e) **GitHub HEAD·충돌·도구 권한**은 원본/HEAD 재조회 후 최소 변경·안전한 재기준화. 허위 PASS나 우회는 금지.

6. **완료 근거 및 다음 작업:** 매 회차 `repo / branch / 정확 SHA / 수정 경로 / 처리 REQ-ID / 구현완료율 전→후(분모 미확정이면 UNASSESSED) / 실행 검사 PASS·FAIL·SKIP·NOT_RUN / P2 이관 / 남은 병목·다음 READY`를 간결하게 기록한다. **코드 없는 정책/문서 수정은 실제 제품 구현 진척 0**으로 표시하며, 코드 작성·검증·커밋이 없으면 '작업 재개 성공'이라 주장하지 않는다. 실제 브라우저 미실행은 검증완료율에도 PASS로 반영하지 않는다.

## 0D. 2026-11-17 작업당 1회 후보·`ㄱ` 4~6개 실제 기능 묶음 (재시도 규칙은 최신 §0H 적용)

> **새 실행 규칙:** 기존 0A~0C의 구현/검증 분리와 재계획·고위험 안전 게이트를 **강화**한다. 과거 작업마다 HOLD/Preview/Intent/합성 테스트만 누적하는 방법은 **실제 구현 진척을 입증하지 못한다**. 현행 최종설계 범위, 제품별 REQ 분모, 프로젝트 고유 권한·실행·보안·비용/권리 제한은 그대로 유지한다.

### 문제의 정확한 구분
- 사용자가 MLA를 검토하며 지적한 **28개 작업에 코드 증거가 있더라도 실제 기능 REQ 30개가 완료된 것은 아니라는 현상**을 일반적인 개발 반면교사로 사용한다. 이 숫자를 다른 제품의 task/REQ 분모로 복사하거나 EAI/해총 진척률로 주장하지 않는다.
- `Preview`, `Intent`, 합성 테스트, task별 `evidence_sha`, 문서상 READY 회전은 **필요한 일부 소스 증거**일 수 있으나 Controller/호출자→실행자/실제 DB·API·FE 연결 등이 빠지면 REQ 구현완료로 계산하지 않는다. 같은 권한 HOLD 계약·안전 문구만 반복 보강하는 것은 일반 P1 진척 우선순위가 아니다.
- **P1은 미구현된 전체 실행 경로의 BE/FE 코드를 실제로 작성하는 단계**이다. 그렇다고 실제 보호된 Git/OS/원본·고객 데이터/외부 전송/실서비스 실행이 허가된 것은 아니다. 코드 구현·국소 안전검사와 운영 GO/전체 수용 테스트는 계속 구별한다.

### 실무 실행 계약
1. **기존 소스부터 REQ/호출 경로 감사:** 실 작업 시작 시 현재 `repo/branch/HEAD`, AGENTS/HANDOFF/STATUS, 확정설계·작업 큐를 확인한 뒤 각각 `REQ-ID → 남은 필수 기능 → caller/callee 연결 → allowed_paths → 수용조건 → source SHA`를 매핑한다. 이미 구현된 모듈·합성 테스트를 반복 생성하지 않고, 먼저 **미완성 기능·실제 연결 경로**를 완성한다.
2. **작업당 1회 완성 목표:** 실제 기능 구현 1회 후보를 목표. 실패 시 동일 원인 초기 최대 2회 개선·격리, 원인 재설계 후 다른 방법으로 추가 최대 2회(총 4회 무진전이면 Sol Max 배치 이관); 필수불가결 차단은 사용자에게 Sol Max 즉시 요청. 조회·문서·CI 재호출·모바일 `ㄱ`은 시도 횟수가 아니다.
3. **두 번 무진전이면 격리 후 재설계:** 초기 2회 실제 무진전이면 해당 SWU만 격리하고 독립 READY를 계속한다. 개선된 추가 2회 실패 시 `SOLMAX_BATCH_PENDING`에 누적·일괄 이관; 중요한 의존성 전체 차단·안전 우회 위험 등 필수 차단은 즉시 사용자 Sol Max 요청. 원본/비밀/DB/필수 CI/GO는 우회 금지.
4. **`ㄱ` 한 회차에 4~6개 독립 작업을 구현 목표로:** 충돌 없는 READY 4~6개(현행 큐에 충분하지 않거나 위험하면 가능한 수만)를 동시 준비/묶음 코드·테스트 작성·커밋한다. 의존/allowed_paths가 겹치면 순서 조정. 문서·HOLD만 추가하다 회차를 끝내는 방식은 지양한다. 횟수 목표는 SLA나 강제 100% 완료 보장이 아니다.
5. **P1→P2 판정:** 각각의 완료 판정은 실제 BE/FE/CLI/DB/API 소스+연결 경로+REQ 수용에 필요한 **코드가 완성됐는지**로 한다. P1 국소 문법/타입/필수 최소 빌드·스모크 및 인증/인가/비밀/권한/외부전송/원본·DB 손실 관련 즉시검사는 유지. 브라우저·Playwright/전체 CI 반복 대기·실기기/전체 보안·회귀·UX는 P2로 이관(`NOT_RUN/DEFERRED_TO_P2`). 기존 필수 자동 CI와 브랜치 보호는 비활성화하지 않는다. 코드 완성 후보는 `IMPLEMENTED_UNVERIFIED`, 실행 수용 증거가 있을 때만 `VERIFIED`.
6. **진척 보고:** `repo@branch@SHA | 실제 구현 충족 REQ/전체 또는 UNASSESSED | 새 기능·소스 경로·호출 연결 | task별 의미 있는 attempts | 국소 PASS/FAIL/SKIP/NOT_RUN | P2 UNASSESSED/LOCKED | HOLD·다음 READY`. task source 증거 개수/합성 테스트 수/파일 수만으로 구현완료율을 가산하지 않는다. P1 코드가 없고 정책 문서만 변경된 회차는 제품 구현 진척 **0**이다.

## 2. Instant 실행을 위한 최소 파일/상태 계약
각 제품의 **확정 설계 정본이 이미 있으면 중복하지 말고 참조**한다.
- 작업 큐 예시 `docs/INSTANT_TASK_QUEUE.json`: 각 `task_id / req_ids / depends_on / allowed_paths / implementation_acceptance / minimal_safety_checks / risk / owner / status / evidence_sha / blockers`.
- `docs/INSTANT_RUNBOOK.md`: `ㄱ` 단일 실행에서 READY 선택→코드 작성→부분 안전검사→SHA 커밋→다음 READY. 교착/고위험은 격리 후 독립 작업으로 이동, 재개 가능한 정확 stop point 유지.
- `docs/ACCEPTANCE_MATRIX.md`: **구현 완성률과 Codex P2 검증 완성률 두 개만** 운영한다. 구현 코드 근거/REQ-ID 및 P2 정확 SHA별 PASS/FAIL/SKIP/NOT_RUN을 추적한다. 가중치/분모 미확정 시 `UNASSESSED`; 출시·고객·OS·상품화 승인 등은 비율 없이 별도 게이트 상태로 기록.
- **1회 실행은 가능 작업을 묶어 최대 처리량을 목표**로 하지만 임의 1%p 보증/기한 보장은 금지. `IMPLEMENTED_UNVERIFIED`는 실제 기능 증명이 아니다.
- 실행 로그: `repo@branch@SHA | 구현 완성률(전→후 또는 UNASSESSED) | P2 검증 완성률(완료/전체 또는 UNASSESSED) | 테스트 PASS/FAIL/SKIP/NOT_RUN | P3~P6 상태(비율 없음) | 차단 | 다음 READY`. 이미 검증한 사실 반복 조사 금지.

## 3. 새 채팅/모델 전환 부트스트랩
1. **역할을 먼저 고정**: 중앙 해총 채팅인지, 특정 제품 개발/독립 검수인지, 개별 해커톤인지. 단순 `ㄱ`은 **현재 채팅/명시된 저장소의 잠긴 미션만** 재개하고 자동으로 다른 레포를 작업하지 않는다.
2. **대상 repo/branch/SHA의 HEAD를 우선 확인**, `AGENTS.md`의 최신 정책 배너를 먼저 읽어 우선순위를 확정. 종전 복원 흐름 `HANDOFF → STATUS → AGENTS → REQUIREMENTS → 최종설계 → 실제 코드`는 **자료 검토 순서**로 유효하지만, 먼저 읽힌 HANDOFF의 구형 작업 지시가 최신 AGENTS와 본 정책을 덮어쓰지 못한다.
3. `HANDOFF`의 가장 최근 유효 항목과 `STATUS`로 완료/차단/중단 지점 확인, REQUIREMENTS/확정 설계와 소스/테스트 교차 검증. 과거 추정치와 code HEAD가 다르면 실제 SHA·실행 결과를 우선, 차이를 기록.
4. 제품별 작업 큐와 담당 소유 파일/PR 확인 후, Instant는 기계적으로 다음 안전한 READY를 구현한다. 설계 큐가 없거나 100% 범위 미확정이면 **High 설계부터** 실시. 사용자 승인 없이 임의 큐를 만들어 전체 설계를 축소하지 않는다.
5. CI/외부 승인/실기기 장벽을 `BLOCKED_EXTERNAL`로 격리. 재시도 1회에서 개선되지 않으면 HOLD; 다른 독립 작업 계속. 완료시 STATUS/HANDOFF에 **정확 SHA·검증/미검증·다음 단위** 갱신.

## 5. 중앙 적용 증거와 한계
- 이 V2.1은 기존 중앙 V2 문서의 **동일 경로 정본 개정**이다. AX Dev Factory 시범의 실제 구현/P2 경험을 반영한 정책이지만 **다른 제품 브랜치의 자동 반영·실제 검증 성공을 의미하지 않는다**. 과거 P2/P3/완성률 설명은 이 문서의 상단 두 지표·7단계가 우선한다.
- 이 문서에 링크한 각 레포/브랜치가 **실제로 수정된 사실은 해당 GitHub 브랜치의 exact SHA 확인이 있어야만 APPLIED**. 중앙 링크나 과거 35repo/80ref 관찰 수치는 원격 전파 증거가 아님.
- 지침 충돌 해소는 최신 문서에 **효력상 우선순위를 명시**하는 방식으로 진행한다. 오래된 기록은 별도로 역사로 남기고 안전 조건은 삭제하지 않는다.
- ChatGPT/Codex **사용자 계정의 글로벌 Custom Instructions 및 로컬 `~/.codex/AGENTS.md`/설정 파일은 GitHub 커넥터로 수정할 수 없다**. 사용자가 해당 UI/로컬에서 최신 정책 붙여넣어야 한다. 편집 가능 여부를 확인하지 않은 상태에서 자동 적용 성공으로 보고하지 않는다.
- 별도 비용/배포/워크플로 권한·보안 변경, 고객 원본 변조, 오래된 CI 이력 재기록, 상품 출시 자동화는 이 문서의 범위 밖이다.
