## 2. 없애거나 줄일 기존 병목

1. **파일 1개당 API/커밋/원격 재조회:** 변경 기능 단위로 코드·테스트를 묶고, 안전한 로컬/승인된 GitHub 도구에서 검증 후 필요한 커밋만 작성한다. 원격 HEAD/CI 재조회는 시작·통합·충돌·마지막 검수 등 필요할 때만. 같은 SHA를 의미 없이 반복 조회하지 않는다.
2. **STATUS·HANDOFF·README 등 여러 문서 매번 동시 갱신:** 역할을 분리한다. STATUS=검증 현황, HANDOFF=복원/다음 단계, README=실행법. **중요 상태 변화가 있을 때 필요한 파일만 수정**한다. 실제 제품의 계약 정본, 법정/공식 제출 기록, 불변 추적 기록은 임의로 생략하지 않는다.
3. **테스트 정의만 증가, 실제 실행 부족:** 테스트 *작성*과 *실행*을 구분한다. 변경 기능 집중 테스트 → 발견 결함 수정 → 통합 지점 전체 회귀. CI 녹색은 그 SHA의 명시 범위에만 유효하다. 미실행·의존성 누락·SKIP을 PASS로 계산하지 않는다.
4. **GitHub API·CI 폴링/중복 빌드:** 동일 기능의 독립 불필요 단계와 문서 전용 CI 재실행을 줄인다. 필수 안전·통합·릴리스 테스트는 유지한다.
5. **주변 작업이 기능을 압도:** 기능 완성 조건 확정 → 코드/테스트 묶음 구현 → 집중 실행 → 오류 수정 → 기능 단위 커밋 → 필요 통합 검증 → 최소 상태기록. 장식 UI/과잉 리팩터링/새 체계 구축은 후순위. 고객용 최소 UX, 보안·권한·데이터 안전성은 MVP부터 유지.

**개발 목표:** 최소 작동 핵심 기능 → 원설계 대비 누락 보완 → 실제 연동 → 보안/복구/호환성 완료 → UI 완성. 3일 BEST/4~5일 표준/7일 경과 시 범위 재평가는 *작업 목표*이지 무검증 완료를 강제하는 일정이 아니다.

## 3. 실행·테스트 역할과 로컬/CI 검증

- **AI가 가능한 것은 AI가 직접:** 무료·승인된 Linux/Windows GitHub Actions 또는 직접 접근 가능한 실행 환경에서 먼저 실행한다. 실사용자의 수동 테스트를 기본 절차로 요구하지 않는다.
- **사용자 PC 전용 차단:** 승인된 로컬 Codex에 저장소의 해당 **정확한 브랜치와 SHA**를 임시로 복제하게 하고, 단일 검증기(`verify_local.ps1`, `verify_local.py`, 프로젝트별 동등 명령)를 실행하도록 준비한다. 사용자가 직접 저장소를 만들 필요는 없지만 로컬 실행에는 임시 체크아웃 및 인증된 권한이 필요하다.
- 단일 검증기는 가능하면 **SHA/브랜치/OS/Python(Node) 버전/기능 테스트/회귀/안전한 CLI 합성 경로/PASS·FAIL·SKIP/로그 위치**를 기록한다. 테스트는 임시 격리 폴더와 합성 데이터를 사용하고 실고객·기존 DB·자격증명/설정을 변경하지 않는다.
- **실외부 API, Gmail/PayPal/OAuth/SEC 실제 요청, NAS 체험권 타이머, 개인정보, 결제, 제출, 공개 배포, 유료 CI**는 구분된 명시적 승인 필요. 테스트용 모킹으로 실제 승인·실운영 검증을 대체하지 않는다.
- 테스트 실패 시 맨 먼저 **재현 환경 문제 / Python·Node 의존성 부재 / 잘못된 테스트 기대값 / 실제 코드 결함**으로 분류하고 최초 실패를 해결한다. 무의미한 재실행·임시 데이터 유실·테스트 회피로 통과시키지 않는다.
- 런타임·Windows 오류는 검증 로그와 traceback을 보고 소스/테스트의 실제 결함을 고친다. 재검증이 안 되면 **UNVERIFIED**로 남기고, 다음 안전한 독립 작업은 진행할 수 있다.
